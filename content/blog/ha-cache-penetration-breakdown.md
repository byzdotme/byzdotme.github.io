数据库压力上来了，第一件事通常是打开缓存面板看命中率，结果它并不低。

笔者做稳定性与高可用这块，觉得这是最难解释的一类告警：告警是真的，指标也是真的，两边就是对不上。一个热门商品的缓存过期，接下来几百毫秒里所有请求都去查库重建，这一小段在整个统计周期里几乎不留痕迹，整体命中率照样好看。另一种情形是有人拿随机订单号不停地查，这些 key 从来没被缓存过，每一次访问都是未命中——量足够大的时候它会把命中率拉下来，量不大的时候同样看不出来。

命中率迟钝是因为它是个比值。分母是全部请求，一个 key 再怎么翻腾，只要它占的份额不大，掉下去的那点数字就淹没在正常波动里。等到这条曲线上能看出问题，通常已经不需要曲线来告诉你出事了。笔者自己的顺序是先看数据库：连接数、慢查询、活跃会话。缓存是原因，数据库是结果，先确认结果那一边的形状，再回缓存里找对应的解释。

两种局面都是「数据库在被回源打」，要加的东西却完全不一样。所以这篇不从方案清单开始，先把回源的请求拆成两种形状看清楚。

这里沿用常见叫法：查询一个不存在的数据，缓存和数据库都没有，叫穿透；一个热点 key 正好失效，大量请求同时回源，叫击穿。

## 穿透：这些 key 为什么永远建不起来

穿透的特征是：请求的 key 在缓存里没有，在库里也没有。缓存这一层对它没有意义，无论查多少次结果都是空，不会有任何一条记录被写进去。

最常见的来源是参数没校验。一个查订单的接口直接拿 URL 里的 ID 去查库，爬虫或者攻击者用随机数字连续请求，每个请求都会真实地打一次库、返回一个空结果。撞库扫用户信息属于同一类：ID 格式完全合法，只是库里没有这条记录。

这两类请求在日志里长得几乎一样，都是「查了一个不存在的 ID，返回空」。区别在来源的分布：攻击流量往往是少量来源发出大量互不相同的 key，正常的无效查询则分散得多——用户手抖输错一位，或者上游传来一个已经被删掉的 ID，都会走到这里。限速只对前者有意义——把限速开在后者身上，挡掉的是真实用户。校验看的是请求本身，限速看的是请求的分布，所以校验要排在限速前面。

处理办法按成本从低到高排下来。

先在入口挡住明显不合法的输入——ID 的格式、长度、业务范围，再对异常来源限速。这一步不引入任何新组件，一个订单号字段收到十六进制串，在这里就该返回 400，根本走不到查库那一步。

校验写在哪一层也值得定一下。放在网关，所有接口共用一份规则，缺点是网关未必知道每个业务字段的合法范围；放在应用里，规则最准确，代价是每个入口都得记得加。常见的分工是网关挡掉格式明显不对的，业务范围留给应用判断。

限速的维度同样要挑。按 IP 限最简单，来源稍微分散一点就绕过去了；按账号或者设备限更贴近业务，代价是同一间办公室共用一个出口 IP 的人会被误伤。单机限速在实例数量多的时候只能挡个大概，真要做全局配额，又得引入一个共享的计数器。

对查不到的 key，可以往缓存里写一个空值标记，让后面同样的请求直接命中。这里有两个容易漏的细节。空值标记要和真正的缓存未命中区分开：如果两者在代码里都表现为「取出来是空」，分支就会写错，想统计查空比例时也拿不到数据。TTL（Time To Live，缓存过期时间）也不宜太长，它直接决定下面那个副作用的窗口有多大。

还有一个状态区分藏在更里面：缓存里没有这个 key、缓存里明确记着「不存在」、这一次缓存压根没访问成功（超时、连接被拒、反序列化失败），是三件不同的事。第三种情况下程序并不知道数据到底存不存在，如果代码把它当成「不存在」直接返回空，一次缓存抖动就会放大成一片「查不到」。稳妥的写法是让缓存访问失败走异常路径，宁可回源一次，也不要把「不知道」当成「没有」。

空值缓存的副作用是新数据被自己的旧查询遮住。刚有人查过一个不存在的订单号，紧接着这个订单创建成功，缓存里那条「不存在」的标记还在，用户点进去看到的就是查不到。常见的补法是创建成功后主动失效对应的 key，同时留一个较短的 TTL 兜底：失效通知丢了的时候，TTL 决定这个错误最长能持续多久。

如果每次来的都是不同的随机 ID，空值缓存基本是无效功。写进去的空值没有第二次机会被读到，它只是把数据库的压力换成了缓存空间的压力，还会把有用的数据挤出去。这种情况该回到入口校验和限速上。

即便用得上，空值缓存也要有容量上限。什么时候写、一个接口最多写多少，最好在实现里定死，因为「不存在的 key」这件事本身是无限的。

布隆过滤器（Bloom Filter）适合「key 空间可枚举、变化也不快」的场景：它排在缓存前面，用一个位数组判断 key 是否在已收录的集合里，说不存在就一定不存在。它的问题在位数组和真实数据之间需要同步——新数据还没写进过滤器的时候，真实存在的 key 会被挡住，业务上表现为「刚创建的东西查不到」。还有一处要看具体实现：标准布隆过滤器的位由多个元素共享，删掉一个元素不能简单把位清零，所以删除要么换计数布隆过滤器，要么靠定期用全量数据重建来兜。

位数组的大小是在内存和误判之间做交易：给得越大，假阳性越少，占的内存越多。插入的元素超过设计容量之后，假阳性率会往上走，这时候得重建，而且往往要连位数组一起放大。重建期间新增的数据写不进旧的那一份，要么双写，要么接受一段误挡窗口。

## 击穿：200 毫秒的重建窗口里挤了多少请求

穿透那一边，缓存从来没存住过东西；击穿这边正好相反，值一直在，只是有那么一瞬间不在了。

击穿盯的就是这个重建窗口。假设一次回源要 200ms，在这 200ms 里，同一个 key 的并发请求都会发现缓存是空的，于是每一个都去查库。数据库看到的是一次查询被复制了很多份——缓存放大的从来不是数据量，是并发。

进程内可以把相同 key 的并发回源合并掉，第一个请求去查，其余的在原地等它的结果，`singleflight` 就是这类做法。它的边界在进程上：十个实例部署就是十次回源。

合并的键也要选对。用缓存 key 做合并键最自然，但如果一次重建会连带写好几个派生 key，而读请求各自盯着不同的派生 key，合并就落空了——两个请求明明在做同一件事，却因为 key 不同各查了一次库。

合并还有一个语义细节值得先记住：等待者拿到的是第一个请求的结果，第一个请求失败，所有等待者就一起拿到这个失败。所以失败结果不能顺手写进缓存，否则一次几十毫秒的抖动，会被合并机制复制成一段时间内所有请求都查不到。

一个带锁的重建流程大致是这样：

```text
1. 查缓存：命中就返回
2. 未命中：尝试获取这个 key 的重建锁
3. 拿到锁：再查一次缓存（等锁期间别人可能已经填好了）
           仍未命中才回源 → 写缓存 → 释放锁
4. 没拿到锁：带一个短超时等待第一个执行者的结果
             超时就返回降级内容，不无限等
```

第 3 步里的两次检查、锁的过期时间、锁的所有权校验，是这套流程最容易写错的三处。少一次缓存检查，等待者会重复查库；锁的 TTL 短于重建耗时，锁会在重建还没结束的时候过期，第二个执行者就能进来；释放锁不校验所有权，会把别人的锁删掉，让第三个执行者直接进来。

十次回源要不要进一步收敛，判断依据是数据库当时扛不扛得住。分布式部署本身不构成理由——「我们用了分布式部署，所以必须上分布式锁」这句话里，前提和结论之间缺了一步。如果一次重建只是按主键查一条记录，十次并发查询在数据库看来不过是几十条语句，为它引入一把分布式锁，换来的是每次重建都多一轮网络往返，以及锁本身的一堆边界情况。反过来，如果一次重建要聚合好几张表、跑一条慢查询，或者正好发生在数据库余量最少的时刻，把它收敛成一次就是划算的。笔者自己更愿意先问一句：这条重建路径上一次到底要查多少东西？

除了「收敛成一次」和「完全不管」，中间还有一条路：不限制回源次数，而是给回源本身加并发上限和超时。数据库那一侧看到的并发被压在一个固定的量级上，超出的请求快速失败或者返回降级内容。这条路不减回源总量，它把瞬时尖峰削成了一个平台——对数据库来说，平台比尖峰好受得多。

重建失败之后等待者怎么办，是这套机制里最容易漏掉的一段。等待必须有超时，超时之后要给明确的错误返回或者降级内容，不能让所有请求一直挂在那次回源上。挂住的请求占着线程和连接，一次本来只影响一个 key 的重建，会顺着连接池扩散成整条链路排队。等待超时还要比上游调用方的超时短一截，否则等待者会先在自己这一侧超时，等于白等一场，还多占了一段时间的连接。

## 逻辑过期：先返回旧值，前提是业务允许

合并回源是让等待者共享一次查询。如果业务允许，还有更省事的做法：让等待者直接把旧值拿走。

逻辑过期的思路是让 key 不真的消失，值里带一个逻辑过期时间，读到它过期之后先把旧值返回给调用方，刷新放到后台做。榜单、商品介绍这类内容适合这么处理，用户看到几秒前的数据，体验上没有区别。

值本身的结构要为此改一下：业务字段之外多带一个逻辑过期时间戳，读的一方拿到之后先看这个时间戳，再决定是直接用还是顺手触发刷新。缓存里的值从此不再等于业务对象，所有读这条缓存的代码都要知道多出来的那一段是什么。

这里有个容易踩空的地方：逻辑过期生效之后，缓存里的物理 TTL 必须还留着，而且要比逻辑过期时间长出一个刷新失败的余量。两者设成一样，逻辑过期刚一到，key 也从缓存里消失了，读请求拿到的是未命中，前面这套设计等于没做。

权限、余额、库存这类决定「能不能做」的判断不能套用。笔者做过一段时间的资金安全，这一层的值不敢交给一个可能已经过期的副本。用旧的余额判断能不能扣款，等于凭空多花了一笔钱；更麻烦的是这种错误不会以超时或者报错的形式冒出来，它是一笔等对账时才发现的差额。

同一个系统里不同的操作本来就可以有不同的承诺，一年半前的[《CAP 的边界：分区期间给不出的承诺》](/blog/ha-about-cap)写的是这件事在网络分区下的样子，落到缓存这条线上，它变成了「哪些 key 允许返回旧值、哪些一下都不行」。

后台刷新同样要合并，只允许一个任务在跑，并且记录最近一次成功时间。刷新一直失败的时候，不能无限期地把「稍微旧一点」当成正常结果。业务要能回答最长能接受多旧，超过这个时间的请求应该报错或者走降级。过线之后不再返回旧值，是缓存层能做到的部分；线画在哪儿，得业务说了算。

刷新的触发方式也值得挑一下。挂在读请求上异步触发最省事，但如果这个 key 突然没人读了，它就永远不会被刷新，下一次有人来读的时候拿到的可能是一份很旧的值——好在有最长陈旧时间兜着。定时任务触发覆盖得均匀，代价是任务本身也成了一条要被监控的链路。两条路都行，得知道选的是哪一条。

## TTL 随机化和预热各自管什么

真正让 key 消失的是物理过期，围绕这个时间点还有两件经常和缓存一起被提起的做法。

TTL 随机化是在同类 key 的过期时间上加一点抖动，管的是大量 key 挤在同一秒过期的情况：一批商品在同一时刻被批量写入缓存，或者定时任务在整点刷新一批配置。对单个热点 key 的击穿，它帮不上忙——那个 key 该失效还是会失效，抖动只是把失效时刻从整点挪到了整点零几秒。

抖动幅度不用大，够把这些 key 分散开就行。给得太大，缓存里最旧的和最新的数据会差出不少，读取方对「缓存里大概是什么时候的数据」也就没底了。

顺带把一个经常混进来的词分开：一大批 key 在相近的时间失效，压力来自数量的叠加，常见的叫法是缓存雪崩。它和击穿的区别在于有没有一个「同一个 key」的焦点。这个区分在排查时很实用，因为两种情况的动作完全不同：一个要把过期时间打散，一个要在重建窗口上做合并。TTL 随机化属于前者。

预热是把一次加载的成本挪到流量到来之前。活动开始前把热点数据加载进缓存，确实能省掉第一波请求的同步重建，但活动期间数据还会更新，进程重启之后缓存也还是空的，后面那条失效和重建的路径一点没变。还有一件事得先解决：预热需要知道预热哪些 key，热点识别本身就是另一项工作。

两件事成本低、副作用小，值得做。它们减少的是回源的总次数，重建窗口里的事，只有合并能解决。

## 用数据区分问题

回到开头那个对不上的局面。同样是数据库压力上来，几种可能的形状不一样，先查的东西也不一样：

| 现象 | 更值得先查什么 |
| --- | --- |
| 命中率很高，但回源集中在少数 key 上 | 回源合并、单次加载耗时、重建失败后的等待策略 |
| 查空比例明显偏高 | 入口参数校验、异常来源限速、空值缓存容量、过滤器同步 |
| 大量 key 在相近的时间失效 | TTL 分布、批量清理任务、缓存节点故障 |
| 命中率很高，业务却读到错误数据 | 值的版本、更新时序、逻辑过期的阈值 |

排查动作可以很直接：取一个时间窗口里的回源样本，按 key 聚合一下。榜上是很多个只出现一次的 key，那是穿透的形状；榜首是同一个 key 反复出现，那是击穿。这一步不需要新的监控系统，把日志里的 key 捞出来数一遍就能定性。

数据库那一侧也有线索。缓存侧按 key 统计基数太大、成本高，SQL 指纹能补上另一半：同一个查询模板在一小段时间内的绝对量，再加上这些查询是不是都返回空，基本能看出压力是从哪条路进来的。

监控至少要能看到回源次数、查空的比例、热点 key 的分布、单次加载耗时，以及数据库那一侧的连接数和错误情况。这里的关键是把「未命中」和「查空」拆成两个指标，合在一起看，穿透和击穿就分不开了。

告警也按这个思路设。全局命中率的阈值告警在这两类问题面前几乎是哑的，更有用的一组是单个 key 的回源次数、单位时间内的查空条数、重建耗时的分位值、连接池的等待时间。这几条里任何一条超标，都能在业务指标恶化之前先响。

整体命中率是个平均值，一个热点被大量廉价命中摊平之后，从曲线上看不出异常，但它足以把数据库打死。它还有一层麻烦：没有 key 这个维度。分 key 统计的基数太大，通常只能按 Top-N 采集或者抽样，所以排查时更实用的一步是先看「回源次数最多的那几十个 key 长什么样」，再回头对全局数字。

## 落地顺序：先挡入口，再合并回源，最后才谈旧值

动手之前先把「现在回源到底有多少」量出来。这一步经常被跳过，直接上布隆过滤器或者分布式锁，改完发现数据库该忙还是忙——真正的原因可能是某个接口在做全表扫描式的查询，和缓存没有关系。

量完之后，顺序建议从最明显的压力源开始：

1. 挡无效输入。改的是接口入口，不引入新组件，风险最低。
2. 合并热点回源。改的是缓存读路径，要处理等待、超时和失败语义。
3. 判断能不能返回旧值。改的是业务语义，得业务方回答最长能接受多旧。

这个顺序和成本是反着的：挡无效输入最便宜，也不改动已有接口的行为；合并回源次之，动用的是进程内或者缓存层的机制；返回旧值最贵，它把「数据可能不是最新的」这个前提交给了业务去承担。

入口拦不住的流量，最后还有一道熔断兜底。它保的是核心链路，代价是这个接口暂时不可用，所以触发条件和恢复条件都要写清楚，不能让它变成一个自动打开就没人管的开关。

每加完一层，都用同样的流量复测一遍，看数据库那一侧的请求数是不是真的降下来了。空值缓存换来的可能是缓存空间的增长，合并回源换来的是等待和线程占用，逻辑过期换来的是陈旧数据——这三笔代价都得有对应的观测，否则很容易出现「数据库压力下来了，问题挪到了别处」。复测用的流量最好和上一次是同一份，压测脚本换了、数据量变了，前后两个数字就没法比。

还有一条纪律：一次只加一层。两层一起上，出了问题说不清是哪一层起的作用。缓存这类改动看着都无害，但它们动的是同一条链路上的时序，叠在一起的时候尤其难判断。

最后留个坑：本地缓存和 Redis 这两层之间怎么保持一致，笔者自己还没理出一条足够干净的路子，先记在这里。
