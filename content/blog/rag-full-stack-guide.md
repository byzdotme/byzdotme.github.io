笔者做的是金融风控方向，其中一块工作是把大模型用在技术方案的风险筛查上：让模型先读一遍方案，指出哪条链路没兜底、哪次外部调用没写超时。模型给的理由通常读起来很顺，麻烦的是它答不上来“你凭什么这么说”。

顺着这个念头往前走一步，就是给公司的技术文档做一个问答入口。要问的问题很具体，比如“退款接口超时后能不能重试”。模型能写出一段通顺的解释，却未必知道这家公司用什么幂等键、超时代表失败还是结果未知、哪一版接口已经废弃。回答越像那么回事，读者越难发现它依据的是通用知识。

RAG（Retrieval-Augmented Generation，检索增强生成）的做法是先查资料，再把查到的内容交给模型组织答案。它给回答增加了可核对的依据，但文档过时、检索漏了条件、模型误读原文，仍然会答错。[最初的 RAG 论文](https://arxiv.org/abs/2005.11401)讨论的也是检索与生成的结合，并没有给出“接上知识库就不会幻觉”的保证。

这篇沿着上面这个文档问答场景走一遍链路，关心的是某个具体问题为什么答错、该改哪一步。笔者自己也是边做边补的，下面有些结论是返工之后才想明白的。

## 先确认资料能回答什么

在做向量化之前，可以先人工查几个问题。如果退款接口的文档里根本没写超时重试的语义，换再贵的检索模型也补不出这条业务规则。

知识库需要区分已生效规范、旧版本说明、讨论稿和故障记录。它们可以同时被检索，可信度却不是一回事：一份两年前的故障复盘里写的重试策略，可能早就被后来的版本改掉了。检索把它们平铺在一个候选列表里，模型只会挑读起来最顺的那条。

每份文档至少要能追到来源、版本和访问权限。更新时同步索引，删除时清掉旧块，权限变化也要传到检索层。所谓“离线准备”会反复运行，不是上线前做完一次就结束。文档更新时按内容哈希比对，只重嵌变化的块；每次都全量重建，索引的更新时间会直接卡住文档发布。

入库前的清洗也在这条线上。同一份接口说明可能在 Wiki、导出的 PDF 和企业网盘里各躺一份，格式还不一样。去重和统一格式如果在入库前没做掉，同一段规则就会有三个块在检索时互相竞争，谁排前面全看运气。

知识库还得有人负责。每份文档挂一个责任人，规则废止时有人来下架，比事后在检索结果里一条条加“此条已失效”的补丁便宜得多。没人负责的文档库，问题不会立刻暴露，等到检索结果开始互相矛盾，清理成本已经很高了。

资料很少时，直接选取相关文档放进上下文也可以作为起点。只有在检索确实能减少输入、改善相关性或落实权限过滤时，增加索引这一步才有明确收益。

反过来，数学推理、代码生成、创意写作这类任务本来就不依赖外部资料，检索只会拖慢它。话术模板、固定格式这类要求，用微调把风格固化下来也比每次检索更省事。

RAG 和微调（fine-tuning）不必二选一。检索方便更新外部资料、保留出处；微调可以改变模型处理任务的方式。微调后的模型同样可以使用检索结果，两者叠在一起是最常见的形态。是否需要训练，应当从现有模型在哪类问题上持续失败来判断，只按“事实归 RAG、风格归微调”分工容易看错方向。

## 两条链路，在文档块处接上

![文档经过解析、切分和建索引；查询经过权限过滤、召回和重排后生成带出处的回答](/images/blog/diagrams/rag-full-stack-guide-01-pipeline.svg)

建索引时，解析器要尽量保住原文结构。PDF 里的表头丢了，表格数值就失去了含义；接口说明的标题和参数表被切到两处，检索结果也可能只剩一串字段。扫描件要先过 OCR（Optical Character Recognition，光学字符识别），双栏排版要按栏读，否则整页文字的阅读顺序都是乱的。这类错误发生在生成模型看到内容之前。

两条链路唯一的交接面是文档块，以及挂在块上的元数据。块里如果只有一段文本，没记它来自哪份文档、哪一版、属于哪个权限范围，在线侧回头补这些信息就得再查一次业务库，权限过滤也好、出处标注也好，都会变得别扭。文档 ID、版本号、章节路径、权限标签、原文位置，这几样在切分那一步一起写进块里最省事。

在线查询则需要留下中间结果：原问题、改写后的查询、召回的块、重排后的顺序，以及最终传给模型的上下文。否则看到一个错误答案，只能反复改 prompt，无法判断错误来自哪里。

两条链路的节奏完全不同，这也是它们要分开的原因。离线那一侧慢一点没关系，一次全量重建跑几个小时也能接受，它决定的是知识的上限；在线那一侧每次提问都要跑一遍，多出 100ms 都要给个说法，它决定的是用户等多久。把两件事混在一个流程里，改哪一头都会牵动另一头。

## 切分要保住规则和它的条件

“退款请求可以重试”与“使用同一个幂等键”如果分在两个块里，前一句可能被单独召回。这个结果在语义上很相关，在业务上却不完整。

![同一段规则在固定长度切分与按结构切分下的两种结果，前者把约束条件留在相邻块里](/images/blog/diagrams/rag-full-stack-guide-02-chunk-boundary.svg)

按什么边界切，直接决定了这类事故会不会发生：

| 切法 | 断点选在哪 | 容易出问题的地方 |
| --- | --- | --- |
| 固定长度 | 每 N 个字符一刀 | 句子、表格、代码都可能被拦腰截断 |
| 按段落 | 空行 | 段落长短差得远，长段落还得再切一刀 |
| 按句子 | 句末标点或分词工具 | 粒度偏细，单句往往缺前提 |
| 递归切分（recursive） | 先按大边界切，超长再降一级 | 分隔符顺序要配，配错了退化成固定长度 |
| 语义切分（semantic） | 相邻句子的向量相似度找断点 | 建索引时多一轮 Embedding，慢且贵 |
| 按 Markdown / HTML 结构 | 标题层级 | 只对结构化文档有效 |
| 按代码语法 | 函数、类边界 | 只对代码有效 |

技术文档可以先按标题和段落切，过长的段落再细分。接口签名、参数表、错误码及对应说明尽量放在一起。一张参数表被切成两半，模型看到的字段就少一半；一段代码从函数中间断开，读的人连它做什么都拼不出来。对于超长代码或表格，要保留能回到原文的位置，不能指望一个统一的字符长度处理所有内容。

`chunk_size` 和 `chunk_overlap` 都是需要试的参数。常见的起点是 `chunk_size` 取 200 到 1500 token：短查询、精准问答偏 300 到 500，需要整段上下文才能读懂的问题偏 1000 以上。块切小，单块信息少，一次得多召回几块才凑得齐条件；块切大，真正相关的那句话会被周围内容稀释，相似度分数拉不开差距。`chunk_overlap` 一般取 `chunk_size` 的 10% 到 20%，作用是让刚好跨在边界上的信息两边都能捞到，代价是重复召回和额外的存储开销。

这些数字是起点，不是答案。文档的写作粒度、提问的长短都会把结论带偏。与其认定某个 token 数是最佳值，不如拿同一组问题比较：相关规则有没有被召回，前提条件有没有跟着回来。想更快看出问题，还可以把关键规则列成十几条，逐条在块列表里搜一遍，看约束和它的条件是不是落在同一个块里。

块 ID 的生成方式也得早点定下来。按内容哈希生成，文档改一个字，它前后的块 ID 会全变，增量更新和引用回跳一起断掉；只按文档 ID 加顺序号生成，中间插入一段内容，后面的位置就整体平移。常见做法是章节路径加序号做 ID，另外存一份内容哈希来判断这个块有没有变。

还有一种办法是小块检索、父块返回。命中某段重试规则后，把它所在的小节一起取出，检索粒度与阅读粒度就能分开设置。具体做法和它的代价，准备另写一篇来讲。

## Embedding 模型怎么选

Embedding 把文本编码成向量，让语义相近的查询和文档更容易匹配。选模型时应拿自己的语言、术语和文档来测。MTEB 这类公开榜单可以帮助缩小范围，却说明不了它能否区分公司里的两个同名服务。

常见的候选和它们的差别：

| 模型 | 维度 | 常见用法 |
| --- | --- | --- |
| text-embedding-3-small | 1536 | 通用场景，单价和延迟都低 |
| text-embedding-3-large | 3072 | 效果更好，存储和调用成本同步上去 |
| BGE（BAAI/bge-\*） | 768 / 1024 | 开源可自部署，中文语料上表现好 |
| M3E | 768 | 开源，中文场景常见 |
| Cohere Embed v3 | 1024 | 多语言场景 |
| Jina Embeddings v3 | 1024 | 支持 8k 上下文，长块不用先截断 |

挑的时候看几个维度。语言覆盖上，中文场景里 BGE、M3E 这类模型常常比通用英文模型更合适。领域适配上，医疗、法律、代码这些语料会让通用模型掉一截，可以拿自己的语料做领域微调。长度上限要提前确认：多数模型只吃 512 token 上下，超过就截断，前面切分留下的长块到这里会白白吃亏。剩下的是成本和部署方式，API 省运维，自部署省单价但要自己扛 GPU。

距离度量也得和模型对上。余弦相似度（cosine similarity）看两个向量的夹角，内积（dot product）在向量归一化后与余弦等价，欧氏距离（Euclidean distance）看直线距离。绝大多数模型输出的向量已经归一化，用余弦或内积即可；对归一化向量来说，欧氏距离的排序结果和余弦完全一致，换个度量并不会多出信息。索引侧配置的度量方式要和建库时一致，只改一头会让排序整体错位。

维度更高通常意味着更占空间、更慢，检索是否更准要拿自己的问题测。文档与查询的向量要使用兼容的模型和配置，切换模型后旧索引不能直接混用。稳妥的做法是保留两套索引，用同一组问题比对结果，再决定切不切。

工程上还有两件小事常被漏掉。批量提交多条文本能减少往返次数，也更容易撞上限流；相同文本反复嵌入是纯浪费，加一层“文本哈希 → 向量”的缓存最直接，缓存键里要带上模型和预处理版本，否则换了模型还在命中旧向量。

榜单挑出来的三五个候选，最终还是要用自建的小测试集分胜负：拿二十来个真实问题，每个改写成两三种说法，看同一个答案能不能被这几种问法都召回，同时看几个“长得像但不是”的问题会不会被误召回。这一步花不了多少时间，比反复研究维度数字管用。

## 索引算法在拿什么换什么

数据量小的时候，先用精确搜索建立基准很有用，至少知道理想情况下能排成什么样。数据量上去以后就轮到近似最近邻搜索（ANN，Approximate Nearest Neighbor），它缩小了比较范围，也可能漏掉本来应当排在前面的向量。

| 索引 | 怎么找 | 拿什么换什么 |
| --- | --- | --- |
| Flat | 逐个向量算距离 | 结果精确，条数一多就慢得没法用 |
| IVF | 先聚类分桶，只搜命中的几个桶 | 快，落在桶边界上的向量容易被漏掉 |
| HNSW | 分层图，从稀疏层快速落到目标区域，再在密集层细找 | 速度和召回都好看，代价是内存 |
| PQ | 把向量压成短码，用近似距离比较 | 省内存，精度会掉 |

HNSW（Hierarchical Navigable Small World）的思路接近跳表：上层节点稀疏、跨度大，用来快速定位；越往下节点越密，用来精挑。它的几个参数值得记住：`M` 是每个节点的连接数，常见取值 16 到 64，调大召回更好但内存和建索引时间一起涨；`efConstruction` 是建索引时的搜索宽度，调大索引质量更好、建得更慢；`efSearch` 是检索时的搜索宽度，调大更准也更慢。线上想调召回率，通常先动 `efSearch`，它不需要重建索引。

以一千万条、1536 维的 float32 向量为例，向量本身占用约 `10,000,000 × 1536 × 4 = 61.44 GB`。这还没算图索引、原文、元数据和副本。压缩后的空间和召回损失取决于配置及数据，不能直接许诺“压到十分之一，精度只降几个点”。建索引的内存峰值往往比稳态占用高出一截，容量按稳态数字规划，重建时容易直接被打爆。

删除和更新的代价也要提前想。多数图索引的删除是打个标记，空间要重建才回收，删得多了检索还会变慢。语料如果更新频繁，重建窗口和双写策略就得一起设计，否则要么检索结果里混着已删除的旧块，要么每次发布都得停一次索引。

向量数据库的选择还要看更新、删除、权限过滤、备份和运维。PostgreSQL 的 pgvector 扩展、Elasticsearch 的 `dense_vector` 字段都能存向量，前者让向量和业务数据躺在同一套备份、权限和事务里，后者本来就有 BM25，做混合检索少接一个系统。Faiss 是索引库不是数据库，增删改、权限和持久化都得自己补，[它的索引说明](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes)把 IVF、HNSW、PQ 这些组合的差别列得很清楚。已有数据库能承担负载时，少维护一个系统本身就是收益；规模和查询方式超出它的能力，再迁移也不迟。百万条以内的语料，pgvector 配 HNSW 通常就够用；到了亿级、又要压内存，再考虑专门的向量库和 PQ 这类组合方案。

## 召回不准，先看漏的是哪类词

“支付没返回结果”与“请求超时”可能表达同一件事，向量检索有机会把它们连起来。但接口名、版本号、错误码不同，即使语义相近，处理方式也可能完全相反：`REFUND_TIMEOUT` 和 `REFUND_REJECTED` 在向量空间里挨得很近，一个该去查单，一个该直接返回失败。

关键词检索在这里补上了另一半。BM25 是这一路最常见的打分函数：一个词在当前文档里出现得越多、在整个语料里越罕见，得分越高，文档长度会做归一化处理。它不懂同义词，但“`REFUND_TIMEOUT` 出现在哪几段里”这种问题，它答得比向量检索干脆。专有名词、错误码、版本号都归它管。中文语料上还多一层分词：分词粒度选得粗，错误码会被切碎；选得细，同一个业务词又会拆成几种写法，同一份文档在不同分词器下的召回结果能差出不少。

两路召回后先去重，再合并排序。同一节的相邻块经常一起进候选，按文档 ID 加章节去重能省下不少额度。RRF（Reciprocal Rank Fusion，倒数排名融合）用名次而不是原始分数合并，公式是 `score = Σ 1/(k + rank_i)`，因此不需要把两路分数归一到同一尺度；加权分数那条路则必须先处理分数尺度，否则量纲大的那一路会直接压过另一路。选哪种方法，看错误样本和评估结果，不必把混合检索当成所有系统的标配。

两路要能合得起来，前提是它们共享同一套元数据和过滤条件。向量库和搜索引擎各存一份文档描述、权限标签只在一边更新，合并时就会出现同一份文档两个版本、或者一边查得到一边查不到的情况。落地时一般让一侧做数据源，另一侧只保留 ID 和检索必须的字段，同步失败也能一眼看出来。

还有一类漏不是算法造成的，是权限过滤把该看的文档挡在了外面。权限条件应当在文档进入模型上下文之前生效：只在生成答案之后做过滤，模型已经读过无权阅读的内容，再删答案也收不回来。缓存、父块扩展和重排都要沿用同一套权限范围，否则绕一圈还是会漏出去。把权限做成检索时的过滤条件而不是事后筛选，顺带还省了算力：按租户或文档类型分区之后，一次查询要比较的向量少一个量级，排序结果不会变，机器少跑很多冤枉路。

## 重排和查询改写，分别补哪一段

重排让模型重新比较查询与候选文档的相关性。常见的交叉编码器（cross-encoder）会把查询和文档拼在一起读，比双塔各自编码多了交互，代价是每个候选都要跑一次前向计算。它能把正确候选往前提，但救不回根本没被召回的文档——重排的天花板由候选集合决定。

粗召回取 20 到 50 条、重排后留 5 到 10 条，是常见的起点。两个数字要分开调：前者决定正确段落有没有机会进候选，后者决定输入给模型的长度和噪声。候选只取 3 条时，正确段落一旦没进来就没有补救机会；取到 20 条以上，无关内容又会把真正相关的段落挤淡。增加重排是否值得，要看答案收益与端到端延迟，套用一个固定的提升百分比没有意义。

重排模型也有几种选择：API 形态的多语言效果好、接起来快，开源的 BGE Reranker 一类中文表现不错、可以自己部署，用大模型逐个候选打分效果最好，代价是每个候选一次调用，几十条候选就是一笔不小的开销。语料只有几百条、或者延迟预算卡得很紧的时候，把重排这一步先跳过，反而更容易把整体调顺。

查询改写处理的是另一类问题。“它支持退款吗”缺少主语，可以从对话历史里补全；比较两个服务的差异，可以拆成两条查询分别检索。还有一种路数是退一步：原问题问“退款接口 v2 在超时 30 秒后是重试还是直接失败”，先退到“退款接口的超时与重试语义”拿到那一节，再回来看具体版本。

一条问题也可以一次生成两三个说法不同的查询，分别检索后合并去重，命中率通常比单条查询好，代价是成倍的 Embedding 和检索开销。候选里如果挤满同一节的相邻块，还可以用 MMR（Maximal Marginal Relevance，最大边际相关性）在相关性和多样性之间折中，把机会让给其他文档。

改写之后要保留原问题，并检查版本号、否定词、租户和时间条件有没有丢失。模型把问题改得更顺，也可能改错问题，而检索侧看不出这个差别。改写和检索的先后也有讲究：先拿原问题检索一次，再用改写后的查询补一次，比完全依赖改写稳妥——改写丢掉的业务词，原问题还能靠关键词检索捞回来。[HyDE](https://arxiv.org/abs/2212.10496) 是另一种思路：让模型先生成一段假想文档，再拿它去检索。假想文档只是检索线索，不是回答依据；涉及内部规则时，结论仍要落回实际找到的资料。

## 生成这一步还能约束什么

检索交出来的片段，最后要靠一段提示词组织起来。系统提示里至少有两句要写清楚：答案只能依据给定的资料；资料不足时说明缺少依据。少了这两句，模型会很自然地用通用知识把空补上，而读者从答案里看不出哪部分是查到的、哪部分是它自己想的。

塞进上下文的块也不是越多越好。位置上有讲究，模型对上下文开头和结尾的内容更敏感，夹在中间的那段容易被忽略，上下文越长越明显，这个现象常被称作“迷失在中间”（[Lost in the Middle](https://arxiv.org/abs/2307.03172)）。重排给出的顺序因此值得保留，最相关的几块放在开头或结尾，别在拼接时又打乱。

块的数量同样要克制。二十块未必比五块准，多出来的部分既稀释注意力，也把 token 成本推上去。加进去的块有没有让答案变准，还是要拿那组评估问题来看。

## 引用要能把人带回原文

回答末尾列出处，是 RAG 相对纯生成最实在的一个好处，前提是这些出处真的能点回去。块上只写文档标题不够——文档改版之后，用户拿着标题进去还得自己翻。文档 ID 加章节锚点，再带上版本号，才构成一个可核对的引用。

版本这一项最容易被省。检索命中一份旧版说明，引用也跟着指向旧版，读者点开看到的恰好是要废弃的那条规则。标注错了比不标更糟：读者会因为出处而相信它。生成时要求模型逐段说明依据来自哪个块，比事后按相似度倒推引用可靠得多，前者还能顺带暴露“这段话没有依据”的情况。

引用的粒度也要挑。标到块，读者还得在整块里找那句话；标到句子，块内偏移量就要在切分时一起存下来，否则事后再对齐只能靠字符串匹配。前端能展开引用块的前后文，比只给一个链接有用：读者往往需要看约束条件，而不只是被引用的那一句。

## 一次查询的时间花在哪

把链路拆开看，各段的量级差得很明显：

| 阶段 | 典型耗时 |
| --- | --- |
| 查询 Embedding | 50–200ms |
| 向量检索 | 10–100ms |
| 重排 | 100–500ms |
| LLM 生成 | 500–3000ms |

大头在生成，这一点在调优时最容易被忘掉：在检索端折腾一下午省下来的几十毫秒，模型多吐两句话就还回去了。查询改写、重排、多查询这几项各自增加一次模型调用或一轮计算，加起来能到几百毫秒，在延迟敏感的场景里要算进预算。能并行的部分就并行：向量检索和 BM25 可以同时发出去，谁先回来都不影响合并。重排虽然本身贵，却能把塞进 prompt 的片段从几十条压到几条，生成那一侧的 token 开销跟着降下来，总账未必亏。

该量的是端到端：检索快了 50ms、生成多花了 300ms，用户感知到的是后者。

能省的地方还有两处。同一个问题在短时间内被反复问到时，缓存整条问答结果比缓存向量更划算，前提是缓存键覆盖权限范围和资料版本；查询改写和向量检索之间没有依赖，也可以先并行发出去，用改写后的查询再补一次检索。

## 评估要能指向下一步修改

笔者更倾向于先收集一小组能人工判断的代表性问题：有明确答案的、跨文档的、带版本限制的，以及资料里根本没有答案的。为每个问题标注支持结论的原文和不能漏掉的条件。只有正例，会掩盖系统“查不到也照答”的毛病。问题的来源也有讲究，把用户点踩的那些、群里反复被问的那些攒起来，比凭空造二十道题更接近真实分布。

错误出现在链路的哪一段，可以按这个顺序缩小范围：

| 观察结果 | 优先检查的位置 |
| --- | --- |
| 正确资料不在候选中 | 文档是否入库、切分、过滤条件、召回方式 |
| 正确资料在候选中，却没进最终上下文 | 合并排序、重排、截断和去重 |
| 上下文有依据，答案仍然错误 | 生成指令、推理、引用对应关系 |
| 找不到资料，却给出确定答案 | 拒答条件、证据充分性判断 |

第四类问题在出题时最容易被漏掉。评估集里要专门留几个“资料里确实没有答案”的问题，标准答案写成“说明缺少依据”，模型给出确定结论就算错。这类题最能暴露系统的过度自信，也最接近真实用户会踩的坑。

检索这一层看 Recall@K、MRR 和 NDCG@K。Recall@K 是 Top-K 里命中的相关文档占全部相关文档的比例，只回答“有没有漏”，不关心排在第几。MRR（Mean Reciprocal Rank，平均倒数排名）取第一个相关结果位置的倒数再平均，适合答案通常只有一处的问答。NDCG@K（Normalized Discounted Cumulative Gain）把位置折损算进去，能表达“相关但不够相关的段落排在了前面”这种分级情况。

检索与生成的质量还要分开看四件事：答案有没有回答问题（Answer Relevance），有没有忠于检索到的原文（Faithfulness），相关检索块是否排在无关块前面（Context Precision），生成答案需要的信息有没有被全部召回（Context Recall）。[Ragas 的指标目录](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)区分了这些维度；只看一个总分，会把这些差别抹平。

用模型给答案打分可以快速筛样本，也带着自己的偏好：答案长一点、格式整齐一点，分数就容易上去。关键结论还得人工抽检。评估集本身也会过期，文档删了、规则改了，对应的问题和参考答案要跟着调整，否则跑出来的趋势只是在衡量一批已经不存在的资料。

评估集负责回答“改得对不对”，线上指标负责回答“现在有没有变差”。检索 miss 率（一批查询里没能召回任何相关块的比例）、点踩率和端到端延迟这三条，是日常最该盯住的。评估集不必每改一行代码就跑，但召回方式、切分参数、Embedding 模型这三类改动值得完整跑一遍，它们影响的是整条链路。
