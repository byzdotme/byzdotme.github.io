接手过一个 Go 和存量 Java 混着的仓库。存量那部分的意思是：能跑、能改，但当年为什么写成这样，眼下没几个人讲得清。这类还没有 AI 规范的老仓，最先察觉到的问题就是它太敢改：不知道哪段代码是历史包袱，也不知道哪套写法已经被换掉了。

让 Claude Code 修改老项目时，麻烦往往不在语法。它可能找到了一个能照抄的接口，却不知道那套写法已经弃用；也可能发现一段重复代码，顺手合并了团队刻意保留的兼容分支。这类偏差一次两次可以口头纠正，次数多了就变成每个新会话都要重新解释一遍的成本。

这些背景值得写下来，但不用把整个项目手册塞进 `CLAUDE.md`。这篇讨论的是信息放在哪里、怎么校验，以及第一次交给团队使用时先试什么。扩展组件的配置放在上一篇[《Claude Code 扩展的四个层次》](/blog/claude-code-ecosystem)里，自定义模型接入准备之后单独写一篇。

## 哪一份 CLAUDE.md 会在什么时机被加载

后面几节的取舍都从这一个心智模型推出来。Claude Code 读 `CLAUDE.md` 有两个方向：

- **向上聚合**：会话启动时，从当前工作目录一路向上找，找到的 `CLAUDE.md` 全部加载。
- **向下按需**：运行过程中读到某个子目录里的文件时，那条目录链上的 `CLAUDE.md` 才被追加进上下文。

![分层 CLAUDE.md 的加载时机：启动时向上聚合的文件，与读到子目录文件时才追加的文件](/images/blog/diagrams/claude-code-team-adoption-01-claude-md-loading.svg)

据此可以把内容分成四层：

| 层级 | 文件 | 写什么 |
| --- | --- | --- |
| 全局 | `~/.claude/CLAUDE.md` | 个人偏好：commit 风格、默认语言、默认模型 |
| 项目 | `<repo>/CLAUDE.md` | 项目铁律、目录地图、命令速查、Skills 索引、风格锚点 |
| 子系统 | `<repo>/<area>/CLAUDE.md` | 这个子系统特有的架构、依赖、常用命令 |
| 模块 | `<repo>/<area>/<module>/CLAUDE.md` | 该模块的历史坑、兼容约束、“动这里前先看 X” |

为什么一个根文件不够用？因为规则的作用范围差别很大。“计费模块的金额一律用 Decimal，不许用 number”只对计费成立，写进根文件却会被拼进每一次会话，包括那些只是在改一行页面样式的会话。规则堆得越多，真正相关的那几条越容易被淹掉。

## 根文件只写每次进入项目都需要知道的事

一份有用的根 `CLAUDE.md`，通常能回答项目做什么、代码入口在哪、如何验证，以及哪些改动需要额外确认。

例如下面这份内容属于假设项目，不能未经核对就复制：

```markdown
# 项目说明

这是一个支付后台，使用 pnpm 管理依赖。

## 入口
- services/api/：HTTP 入口
- packages/billing/：计费与退款规则
- docs/decisions/：已确认的设计决策

## 修改约束
- 保持现有公开 API 兼容；确需改变时先说明影响。
- 金额沿用现有 Money 类型，不自行引入浮点计算。
- 不记录 token、完整卡号或未脱敏的个人信息。

## 验证
- pnpm typecheck
- pnpm test
- 退款改动还需运行对应集成测试。
```

命令必须来自当前仓库。模型扫描后生成的初稿，需要有人实际跑过再认可。把一条错误命令写进长期指导，会让以后每次任务都在同一处失败一次。

值得单独留一节的还有“怎么找代码”。它相当于写给 Claude Code 的 README，写清楚入口从哪个 glob 开始、领域模型先看哪个目录、定时任务在哪，能省掉大量无谓的 glob 和 grep：

```markdown
## 怎么找代码
- API 入口：从 `services/api/src/routes/**` 开始
- 领域模型：先看 `packages/domain/src/<aggregate>/`
- 外部集成：`services/api/src/integrations/<provider>/`
- 定时任务：`services/worker/src/jobs/**`
```

反过来，有几类内容放在根文件里是纯亏：大段 API 文档应该进 `docs/`，需要时用 `@` 引用；只在某种场景下才用的步骤应该写成 Skill；机器生成的目录树和文件清单不必抄，Claude Code 自己 `ls` 一次拿到的就是最新的；密钥和客户数据更不能进来，因为这份文件会进上下文。

自然语言规范是工作指导，不是访问控制。禁止读取密钥、限制外部写入这类要求，还要落实到权限、沙箱和服务端账号上。

## 只影响一块业务的说明，放在那块业务附近

项目变大以后，可以在子目录补 `CLAUDE.md`：

```text
CLAUDE.md
backend/
├── CLAUDE.md
└── billing/
    └── CLAUDE.md
```

根文件保留全局约定，billing 文件说明金额模型、状态变化和兼容包袱。个人偏好放在 `~/.claude/CLAUDE.md`，不必要求全团队共用。[记忆与项目指导](https://code.claude.com/docs/en/memory)

子系统那一层最值得写的是四样东西：这个目录的风险级别、下面的子目录各自负责什么、不能破坏的不变量，以及“动代码前先看”的踩坑记录。踩坑记录尤其划算，它记录的是从代码里读不出来的事实——某个回调不保证到达顺序、某个对账任务要留宽限期、汇率表每天凌晨才更新一次。这些看代码要猜很久，写下来只要一行。

局部说明要解释原因。例如“不要调整旧对账导出的列顺序，下游财务导入仍按列位置读取”，比单写“禁止重构”更有用。依赖方迁移后，也能知道这条限制何时可以删除。

越专有的规则越该往深处放，只有全局铁律才配进根文件。但目录分层不该机械地铺满四层：一个没有特殊规则的模块，不需要专门创建空文件。规则是踩坑攒出来的，不是一次写完的，所以隔一段时间要回头删掉已经失效的条目——迁移做完了、模块下线了，对应的规则就该跟着走。

## 横跨目录的规则，用 paths 表达

如果规则是按文件类型划分的，而不是按业务模块划分的，可以用 `.claude/rules/`：一个文件一个主题，用 `paths` frontmatter 声明作用范围。

```text
.claude/rules/
├── code-style.md      # 没有 paths，全局加载
├── api-handlers.md    # paths: src/api/**/*.ts
└── migrations.md      # paths: db/migrations/**/*.sql
```

例如下面是测试文件的规则示意：

```markdown
---
paths:
  - "src/**/*.test.ts"
---

# 测试约定
- 沿用相邻测试的 fake 和 fixture。
- 不依赖真实生产账号或当前墙上时间。
- 回归测试应能区分修复前后的行为。
```

有 `paths` 的规则在读取匹配文件时生效；没有 `paths` 的规则会无条件加载。不要以为放进 rules 目录就一定节省上下文。[路径规则说明](https://code.claude.com/docs/en/memory#path-specific-rules)

两套机制怎么选，看规则是跟着文件类型走还是跟着目录走：

| 用 `.claude/rules/` | 用子目录 `CLAUDE.md` |
| --- | --- |
| 规则按文件类型或 glob 组织，例如 `*.test.ts`、`migrations/**` | 规则按业务模块边界组织 |
| 同类规则要在多个目录复用 | 单个目录强本地的踩坑记录 |
| 想细到“只在改迁移脚本时加载” | 模块级“动这里前先看 X” |

两者可以并存。要留意的是 `rules` 和 Skill 的 `paths` 写法很像，语义却不同：rule 是常驻片段，匹配时把整段 markdown 拼进 system prompt；Skill 是按需触发，匹配时只把 description 注入索引，正文要等它决定调用才加载。“测试应遵守什么”适合规则文件；“按哪些步骤排查一类失败”更适合 Skill。相同段落没有必要在根文件、rules 和 Skill 里各复制一遍，重复版本迟早会产生分歧。

## 老仓库先调查一条真实流程

“全面理解代码库”很容易产出一份看似完整、却没有验证过的目录介绍。第一轮可以更具体，例如调查退款从接口到状态落库的过程：

> 先只读。定位退款入口、身份校验、状态变化、网关调用和回调处理，给出代码位置。区分当前实现、已弃用代码和无法确认的部分，并列出实际可运行的相关测试。不要修改代码或指导文件。

沿一条业务流程阅读，可以同时发现内部框架用法、错误处理和测试习惯。想让这一步更成体系，就把侦察清单直接交给一个只读子代理：语言、构建系统、包管理器、测试框架和 lint 工具分别是什么；每个顶层目录负责什么；用到了哪些内部包，各自出现在多少个文件里、典型用法在哪两个位置；哪里存在“同一件事有多种实现”的历史沉淀；单测、集成和端到端测试各自分布在哪；以及危险区域——循环依赖、超过千行的上帝文件、`git log` 里改动最频繁的热点文件。清单末尾加一句“没把握的地方明确写 UNKNOWN”，比让它猜要值钱得多。

之所以派给子代理，是因为 grep 和批量读文件这些脏活跑在它自己的上下文里，主会话只收到一份摘要，不会被海量源码撑爆。确实有互不依赖的大块调查时，再并行拆给多个子代理；按“超过多少文件就自动拆”切任务没有意义，那只会切出一堆互相不知道对方结论的碎片。

判断热点文件也不必靠感觉，git 本身就是现成的信号：

```bash
# 最近三个月的热点文件
git log --since=3.months --name-only --pretty=format: | sort | uniq -c | sort -rn | head -20

# 某个关键字是什么时候进来的
git log -S"<关键字>" --oneline
```

基于证据整理出指导初稿后，让熟悉模块的人检查：它是否把偶然写法当成了规范，是否遗漏关键的兼容条件，是否把规划中的能力写成已经实现。

## 示例代码要标明值得学的部分

团队可以引用一个维护良好的模块：

```markdown
## 参考实现
- src/modules/order/：参考错误映射和请求校验。
- src/modules/inventory/：参考测试 fixture 的组织。
- src/modules/legacy-pricing/：仅维持兼容，不作为新模块模板。
```

这里的路径仍是示例。真实文件不能只因为“资深同事写的”就当作标准答案，要说清哪些方面值得参考：命名怎么起、日志怎么打、错误类型怎么定义、注释密到什么程度。这些隐含规范已经被代码固化了，模型的模仿能力又强，指明样本比在根文件里堆几十条风格规则更管用。

反过来说，一个模块的测试组织很好，不代表它的所有历史实现都应该复制。所以“好样本”最好带上限定词，比如写成“参考测试 fixture 的组织”，而不是笼统地推荐整个目录。

## 用一个小改动检查规则是否真的有用

规则写完，怎么知道它有用？挑一个边界明确的任务，让 Claude Code 按指导实现，再看 diff 和验证输出。重点观察是否找到了正确入口、保留兼容行为、遵守身份与金额约束，以及有没有真实运行测试。

更完整的做法是把它当成一轮校准：先挑一个小 bug 或小重构，让它走 plan 模式；拿到 diff 后严格 review，凡是不符合团队风格的地方就回写到 `CLAUDE.md` 或对应的 Skill，而不是当场口头纠正——口头纠正只对这一次会话有效，回写才对下一次有效。然后再做第二个小任务，看偏差是否还在。

发现偏差后，先判断原因。缺了项目背景就补背景，命令失效就修命令，测试本身不覆盖行为就补测试。不是每个错误都值得再加一条“必须”。

团队共用的指导与 Skill 可以走普通评审流程，个人凭据留在本机或组织的密钥系统。后续维护时，删除失效规则和补充新规则同样重要。一份短而准确的项目说明，比一份不断累积禁令、却没人敢删的文件更容易长期使用。

至于分层写到第四层以后，几份文件之间开始互相矛盾该怎么办，笔者目前也没有好答案，先把这个坑记在这里。
