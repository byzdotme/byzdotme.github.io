笔者在资金安全方向做过一段时间。账务这一层在整条支付链路里看起来最没有技术含量：一张余额表，几条更新语句，接口文档一页能写完。它也是笔者见过最难改的一层——收银台可以重做，路由规则可以调，通道接不进来换一家就行；账本一旦上线，动一次要连带动历史数据、对账口径和下游报表。

几个月前在[《支付单据与状态：把一次付款追踪清楚》](/blog/pay-core-model)里把一次付款拆成了交易单、支付单和通道尝试，回答的是「这笔钱算不算付成功」。再往下还有一层：钱记在哪个账上，凭什么这么记。

只看接口的话，账务确实像两条语句：

```sql
UPDATE account SET balance = balance - 100 WHERE account_id = 'user_A';
UPDATE account SET balance = balance + 100 WHERE account_id = 'merchant_B';
```

它们在语法上没有问题，麻烦在于只留下最终数字。执行完第二天客服转来一句「客户说钱没到」，你手上只有 A 少了 100、B 多了 100 两个当前值，中间经过了哪笔业务、哪次通知、有没有重复执行，一概查不到。数据库抖动、网络超时、并发覆盖之后，这个缺口没有东西能补。

核账能不能做，取决于当初账是怎么记的，这是笔者在那段时间里体会最深的一条。要把上面这两条语句变成一本能追的账，得先换掉记录方式。

## 先确定站在哪个主体的账上

借和贷不能简单翻译成「扣钱」和「加钱」。它们表示会计记录方向，具体如何影响余额，取决于科目性质和记账主体。同样一个「贷」，记在商户待结算应付款上，意思是平台欠商户的钱变多了；记在手续费收入上，意思是平台自己的收入增加了。这两类混进一个科目，月底出报表的时候就答不上来「这 5 元到底是不是平台赚的」。

例如，假设某平台账上已经有对用户的 100 元应付款，本次交易将其中 95 元转为对商户的应付款，5 元按约定确认为平台收入。只为说明这个假设下的平衡关系，可以记成：

| 方向 | 科目 | 金额 |
| --- | --- | --- |
| 借 | 用户应付款 | 100 |
| 贷 | 商户待结算应付款 | 95 |
| 贷 | 手续费收入 | 5 |

这个例子没有描述银行账户之间的真实划拨，也没有覆盖税费、收入确认时点和监管要求。具体科目应由业务与财务确认。把用户资产减少、平台负债增加和平台收入混在同一本账里，会把主体弄乱。

凭证和分录是两个层次。凭证记录业务事件——哪张支付单、什么时间、谁发起；分录记录这次事件让哪些科目动了、动了多少。支付系统把「这个订单付了 100 元」交给账务，账务把它翻译成一组带方向、科目和金额的分录，再去动账户。这层翻译看着多余，换来的是两件事：业务系统不用知道会计科目怎么定，到了日终，财务能拿着一批凭证去和渠道账单核对，而不是对着一张说不清来路的余额表。

复式记账（Double-Entry Bookkeeping）常被说成「保证了资金安全」，这个说法靠不住：借贷平衡只提供校验，试算平衡能通过，账却可能是错的。整笔金额写错，借方贷方一起多写一个零，合计照样相等；对象记错，该记给商户甲的 95 记到了商户乙头上，两边合计不变；重复记账，同一笔支付通知处理两遍，两套分录一起进了账，合计还是相等。这三种错误要靠三样不同的东西拦：重复靠幂等键和唯一约束，金额和对象靠明细与流水的逐笔核对，最后兜底的是每天和渠道的对账。

科目和主体决定了账本长什么样，另有一个更物理的决定落在余额表上：一行代表多大的范围。按「账户 + 币种 + 业务线」拆成多行，写入自然会散开一些，代价是每次查询和报表都要跟着聚合；一个账户只留一行，记账最省事，所有的流量也就压在这一行上。

## 热点发生在共同更新的那一行

假设很多笔交易都要累计到同一个商户余额或平台手续费余额。付款方各不相同，汇总一侧却竞争相同记录。更新频率越高、持锁时间越长，排队越明显。

难点正在这个不对称上。付款方那一侧，每个买家扣的是自己那一行，几笔扣款互不相干；加钱这一侧，所有交易最后都要落在同一个商户待结算账户，或者同一个平台手续费收入账户上。直播带货这类场景最容易撞上：买家各付各的，钱却在往同一个账户里挤。

容易被顶成热点的账户，共同点都是「多对一」的汇点：平台手续费收入账户，每笔交易都要分一笔进来；大商户的待结算账户，分散在各处的付款往一处落；平台自己的营销资金池和分账场景里的过渡户，参与者越多，汇得越急。

数据库这一侧发生的事很朴素。每一条 `UPDATE account SET balance = balance + 95 WHERE account_id = 'merchant_B'` 都要在那一行上加行级排他锁（exclusive lock，X 锁），锁到事务提交才释放。同一行的更新没有并行可言，只能一条一条来。

同一行上的更新只有两种结局：拿到锁往前走，或者等。两笔更新哪怕只差 1 元、SQL 一模一样，第二条也得等第一条提交。也有人第一反应是把余额挪进 Redis 或者本地内存里算，攒够一批再写回数据库——数据库那一行的锁确实松了，但账面事实也跟着挪出了本地事务，进程一挂，先丢的就是它。

排队拉长以后，症状分三档，最后一档最要命：

* 单笔请求卡在锁上，响应时间从一次页内更新变成一次等锁等待。
* 等锁超过 `innodb_lock_wait_timeout`，语句直接报错回滚，业务侧看到一个和「余额不足」毫无关系的失败原因。
* 等锁的线程占着数据库连接不放，连接池被吃满，同一实例上不相干的接口也开始拿不到连接。热点账户最典型的故障形态，是把整库的连接和线程一起拖下水——那一行数字反而是对的。

![热点账户：付款方各改各的行，加钱这一侧在同一行上排队等锁](/images/blog/diagrams/pay-account-01-hot-row.svg)

图上那条队列是 InnoDB 的行锁等待队列，队的尽头只有一行记录；队首那个事务提交之前，后面的请求一步也动不了。把连接池调大一点，只是让更多请求排进同一个队。所以遇到这类告警，先把等锁的现场看清楚。

## 先查锁等待和事务范围

MySQL 8.0 可以直接看当前在等什么：

```sql
SELECT * FROM performance_schema.data_lock_waits;
SELECT * FROM performance_schema.data_locks;
```

`data_lock_waits` 回答的是「谁在等谁」，`data_locks` 给出每一把锁落在哪张表、哪个索引、哪一行上。要问的问题有三个：等的是不是余额那一行；持锁最久的那个事务已经开了多久；那个事务里到底做了多少事。

顺便排掉一个常见误判：余额查询本身通常不是元凶。InnoDB 的一致性读走 MVCC，普通 `SELECT` 不加锁，读得再多也不会互相排队。能把这一行锁住的只有写——`UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 这类加锁读，以及撞上同一个唯一键的插入。

常见的放大器有两个。

**事务范围**。更新余额之后，事务里又调了一次风控、一次账务核心的远程接口、一次 HTTP 通知，持锁时间就从一次页内更新变成了几个网络往返。锁在事务提交时才释放，事务有多长，队首就占多久。把远程调用挪出事务，通常比换一套记账方案便宜得多。

**索引**。`UPDATE account SET balance = balance + 95 WHERE merchant_id = ?` 里的 `merchant_id` 如果没有唯一索引，InnoDB 得扫过并锁住更多记录，锁的范围从一行变成一批行，热点就扩散到了本来无关的账户上。这类问题看起来很有迷惑性：业务代码里的更新条件明明只写了一行数据。

**定时任务和交易抢同一行**。计提、结息、给商户补账这一类批处理，如果落在同一批热点账户上，等于在一个本就很窄的队里又插进一批长事务。它们的执行时间由运维窗口决定，热点却由流量决定，两者错开的时候看不出问题，撞上的那天排队会突然变得很难解释。排查时把同一时间段的调度记录和慢查询日志拉出来对一遍。

这两条排掉之后，如果等锁仍然集中在余额行上，而且事务已经短到不能再短，才轮到考虑改账本结构。先拆账户，可能只是把复杂度加到原来的瓶颈上。

现场长什么样才算对上了怀疑？在 `INNODB_TRX` 里看持锁事务的 `trx_started`，如果它已经过去几百毫秒，而对应的业务 SQL 只有一条 `UPDATE`，那基本可以断定事务里还夹着别的东西；反过来，事务都很短、锁也都只落在余额那一行上，这才是真的撞上了热点账户本身。

## 哪些值可以晚一点计算

如果每笔交易都要立即影响可提现余额，就不能随意延迟更新。相反，某些统计或展示汇总可以从已可靠保存的分录异步计算。两者的正确性要求不同。

落到具体判断上：用户还能不能花、这笔支付放不放行、退款额度够不够，这些值延迟一秒，就可能放过去一笔本来就该拦下的交易；商户「昨日待结算」的展示数字、风控用的累计消费统计、给运营看的日报，晚几秒钟没有人会因此做错决定。

把常见的几个值排一下，口径就清楚了：

| 值 | 什么时候必须准确 | 晚了的后果 | 兜底手段 |
| --- | --- | --- | --- |
| 可提现余额 | 用户点提现的那一刻 | 提走本不该提的钱 | 提现时的原子扣减加额度约束 |
| 付款可用余额 | 受理扣款的那一刻 | 放行了付不起的单 | 受理时同步扣减，不异步 |
| 商户待结算展示 | 秒级以内 | 商户看到一个旧数字 | 汇总任务补上 |
| 风控累计统计 | 分钟级以内 | 少拦一部分风险 | 离线重算，事后补拦 |

这几种要求不能互换。把可提现余额也做成异步，账面上不会立刻出错，只会在某个用户点提现的那一刻暴露成超发。

真要把「加钱」异步掉，有四件事得先答上来：

1. **权威事实落在哪。** 是分录表里的那几行记录，不是余额表里那个数字。余额是可以重算的派生值，分录丢了就再也补不回来。
2. **什么时候算受理成功。** 扣款成功那一刻，分录和待处理任务必须已经在库里；调用方拿到「成功」之后，系统不能因为一次进程重启就把这件事忘掉。
3. **中间不能有丢失窗口。** 分录落库、待处理状态置位、事件发出去，这三步若各做各的——先发 MQ 再写库，或者先写库再发 MQ 而没有补偿——总有一个窗口会让某一笔钱停在半路。稳妥的落点是本地事务里同时写分录和待发送任务，再由投递进程去发。
4. **消费端能去重和恢复。** 消息会重复投递、会乱序、会在消费失败后重来。按业务单号做唯一键是最基本的；再往上要有积压监控和补数入口。

第 3 条最容易被跳过：它要求的改动并不大，但它决定了故障时钱会不会停在半路。

## 削峰：扣款同步，加钱进队列

第一套做法把两端分开：买家付钱这一步同步扣款——用户当场要看到钱扣了；商户加钱、平台手续费累加则写进消息队列（MQ），由消费者按自己的速率慢慢记账。余额行被更新的频率，从跟着下单速率变成跟着消费速率，购买洪峰被拉平，锁等待跟着下降。

队列只能削峰。去重、顺序、必达，这三件事它一件都不提供，全都要自己补。所以这套方案真正的设计点在受理边界上：扣款必须在本地事务里完成并留下分录，然后才把「给商户加钱」作为一条待处理任务投出去。消费端按业务单号幂等落库，重复投递收敛到同一个结果，「先收到 2 号单再收到 1 号单」也不能让余额算错。

幂等键要用业务单号，不要用消息 ID。消息重投和换队列的时候，消息 ID 是会变的，业务单号不会；键选错了，重复消费就变成重复入账。

代价是商户余额变成最终一致。有人问「这笔订单到底入账了没」，系统得能回答中间态：分录已经记下、余额还没加上。只回一句「余额没变」，等于什么都没说。积压也要盯：消费积压的深度除以消费速率，就是商户看到余额的延迟，这个数字要能随时报出来。

能异步的账户是有范围的。加钱那一侧本来就可以晚，套用得上；扣款那一侧一步都省不掉。如果热点恰好落在用户可提现余额上，队列削峰帮不上忙，只能回去把事务做短，或者走拆分那条路。

消费失败还得有重试上限和死信出口。一条反复失败的消息如果没地方去，会把整个消费位点堵在那里，余额的滞后时间从几秒涨到看不见头——而积压监控报出来的只是「队列很长」。

## 汇总：先落明细，定时合并余额

第二套做法走的是流水表：热点账户收到加钱请求时不更新余额表，只往流水表插一条明细；后台任务每隔一小段时间，把这一批流水按账户 `SUM` 出来，一次性 `UPDATE` 回余额表。如果一个账户每秒要被更新一万次，这套做法把它变成每秒一次。

这套方案常被一句「INSERT 不存在行锁冲突」带过，这句话不成立。InnoDB 里插入前的加锁至少有三种会撞上：

* 插入之前要先在目标间隙上加一把插入意向锁（insert intention lock）。往不同位置插的两个事务不会互相挡，往同一个位置插，后一个要等前一个。
* 唯一索引上的冲突会加共享锁，`INSERT ... ON DUPLICATE KEY UPDATE` 遇到重复键加的是排他锁。用业务单号做唯一键来去重，走的正是这条路。
* 另一个事务如果正持着这段间隙的间隙锁，插入会被直接挡住。范围更新、没走对索引的加锁读，都会留下这种锁。

[InnoDB 锁文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)把这些锁分别列了出来。

那它为什么还是有效？因为流水表的插入按业务单号散落在不同的索引页上，争用从「一行」摊到了「一片页」，量级完全不同。判断一套记账方案有没有真的减压，看的就是它把并发落到了多少行、多少页上。

要用这套方案，几个细节得定死：

* 批次范围必须确定。按流水自增 ID 圈一段水位，或者按时间和状态圈一批，处理完打上批次标识。否则任务重跑一次就是重复累加，而这种错误在余额上很难看出来——它只是多了一点钱。
* 水位要留安全距离。多个事务并行写流水时，小 ID 可能比大 ID 后提交；水位贴着最新 ID 走，会漏掉还在路上、ID 更小的那条明细。
* 查询口径要写清楚：返回的是「已汇总余额」，还是「已汇总 + 未汇总明细」。在途支付和退款占用只算前一部分，就会算少。
* 余额表上仍然是同一条 `UPDATE`，只是频率降了。批量越大收益越高，余额的可见延迟也跟着批次间隔走。
* 批次本身要有状态：待汇总、汇总中、已汇总。任务跑到一半挂掉，重启后得知道这一批做过没有；只留一个「上次跑到哪个 ID」的变量，重复累加和漏记都会出现。
* 流水里不只有加钱。冲正、退款、手续费调整会带着负号或者另一个方向落进同一张表，汇总逻辑得认得这些方向，否则只加不减的账迟早对不上。

水位具体怎么推，一种常见做法是：每次都取「上一批水位之后、当前时间往前 N 秒之前」的流水，那 N 秒就是留给乱序提交的等待窗口；处理完再把水位推到这一批的最大 ID。N 取多大，取决于流水写入事务的提交分布——取小了会漏，取大了余额就更晚。

任何一次汇总任务重跑，都必须算出和上次一样的结果。这是这套方案能不能上线的门槛。

## 拆分：一个账户分成很多行

第三套做法把单点摊开：把一个热点账户在物理上拆成 N 个子账户，例如 `platform_fee_01` 到 `platform_fee_100`。入账时按支付单号或用户 ID 做 hash 取模，落到其中一行；需要总额时，把 N 行加起来，或者再由一个任务合并回主账户。

拆掉的是物理行，会计主体没有变。这一百行加起来，对应的仍然是同一个商户待结算应付款，这一点要在科目和报表上体现出来。少了这层对应，分片数一多，就没人说得清这些行合起来究竟代表谁的钱。

写入侧的收益是直接的：单行锁竞争分成 N 行，等待时间大致按分片数下降。这个收益在只往里累加的账户上最实在。代价则集中在读和判断上：

* 余额查询从读一行变成读 N 行再相加，SQL、缓存和报表都要跟着改。
* 如果这个账户还要回答「能不能花」，跨分片的额度判断会变得很难做对——判断要读全部行，读的那一瞬间还可能有人在写。
* 对账要按分片还原，差错定位多一层。

分片维度也得挑。按支付单号取模分散得最均匀，但同一个商户的多笔入账会落到不同行；按商户 ID 取模，单个商户又重新挤回一行上。热点发生在哪个维度，决定该按什么分。合并任务本身还要幂等：重跑、或者跑的过程中有人查询，都得能拿到一个确定的口径。

查询侧一般有两条路：查询时把 N 行实时相加，或者另外维护一个带缓存的总额。前者简单，代价是每次查询都要读 N 行；后者快，但那个总额字段自己又会长成一个新的热点行，等于把刚挪走的问题请回来一次。

提现从哪一行扣，是这套方案最容易漏掉的一环。从主账户扣，主账户立刻变回热点；从子账户扣，又得先把 N 行的可用额度和提现额度对齐。分片数也不是越多越好：N 越大，读取时的聚合成本和合并任务的复杂度一起上涨，够用就行。

所以拆之前先回答一个问题：这个账户的操作里有多少是「加」，多少是「能不能花」。全是加，拆开就有收益；一半是判断，拆开只是把难题换个地方放。

## 三套方案各自把代价放在了哪

三套做法放在一起，真正要比较的是它们各自动了哪个维度、又把什么推给了别人：

| 做法 | 动的维度 | 收益从哪来 | 新增的代价 | 不适合的情况 |
| --- | --- | --- | --- | --- |
| 削峰：扣款同步，加钱进队列 | 时间 | 余额行的更新频率跟着消费速率走 | 余额最终一致，链路上多一段要监控 | 可提现余额这类必须即时准的值 |
| 汇总：先落明细，定时合并余额 | 次数 | N 次加钱合成 1 次，余额行被写的次数下降 | 可见延迟，批次范围和水位要自己管 | 需要逐笔实时余额的场景 |
| 拆分：一个账户分成很多行 | 空间 | 单行锁竞争的等待时间按分片数下降 | 查询、额度判断、对账都变复杂 | 频繁做额度判断的账户 |

它们动的其实是同一件事：把「余额这一行什么时候必须准确」换成一个更细的分工——哪一部分必须当场准确，哪一部分可以晚，晚多久，出了偏差谁来兜。这个分工一旦定下来，就写进了账本结构、任务水位和每天的账务流程里，比任何接口都难改。开头那句判断到这里算是有了依据：账务那一层看着最没有技术含量，改起来却最贵。

账记清楚之后，下一个问题是这笔付款该走哪家通道，路由那一层准备另开一篇。
