让 Agent 改一个函数，通常几分钟就能看到 diff：函数体不长，调用关系清楚，改完跑一下测试就知道对不对。

把任务换成「读懂一个旧模块，补上测试，再把接口迁移到新写法」，同一套工具立刻不够用。它要先把模块入口找出来，弄明白三个调用方各自依赖哪些行为，判断哪些分支是给历史兼容留的，再决定改哪一层，中间还会撞上几条没人维护的测试。跑到一半上下文快满了，它开始忘事：前面确认过的兼容要求，后面又当成没有结论的问题重新讨论一遍。

前一类任务靠的是模型能力，后一类任务考验的是模型外面那一圈东西。这圈控制逻辑现在有个统称：运行框架（harness）——决定什么时候调用模型、往上下文里放什么、输出怎么解析和验证、失败之后从哪里接着跑、状态存在哪。

笔者在资金安全方向做过一段大模型应用的探索，也在 LangGraph 上搭过多 Agent 的流程。那段时间最直观的体会是：把模型接进一条真实链路，工作量的大头不在提示词上，而在链路本身——它在哪里断、断了怎么接上、凭什么说这一段做对了。日常写代码笔者也一直在用 Claude Code 和 Codex，坑是同一批坑，只是换了个地方踩。下面这些经验里，有几条是踩出来的，有几条笔者自己也没完全做到。

这篇讲的是一次任务内部的这些事。任务是反复跑起来、由系统自己找活干之后会多出哪些问题，属于另一批，笔者打算另写一篇来谈。

## 上下文从当前决策往回找

以接口迁移为例，Agent 需要知道旧接口的入口在哪、谁在调用、兼容要求是什么、改完用什么命令验证。整个仓库的架构介绍可能有帮助，但几年前的评审记录、无关模块的源码、已经推翻的尝试，不必一直挤在当前输入里。

可以按作用把信息分几类，倒不必给每一类都建一套系统：

- 项目约定说明允许做什么。这类内容应该沉淀在仓库里的规则文件，而不是每轮对话里重复贴一遍。
- 需求和示例说明结果长什么样。一个符合项目风格的改动示例，往往比十条风格规则更能约束输出。
- 源码、测试和文档提供判断依据。检索回来的资料要带上来源和时间；旧设计文档和当前代码冲突时，把冲突交代出来，不要让模型自行拼成一个看起来一致的故事。
- 进度记录说明现在走到了哪一步。

工具描述也算上下文。写清楚这个工具做什么、什么时候不该调用它，比只写一句功能说明有效得多——模型在边界上的失误，很多来自工具描述只写了正向用途。反面约束经常比正面指令更管用，「不要在这里重试」比「请谨慎重试」更难被忽略。

还有一处容易被忽略：当前任务的状态应该作为独立的结构化块注入。混在对话历史里，它只能等模型自己翻出来——而历史会被压缩、被改写，状态跟着一起变形。

最容易犯的错是全都塞进去：整个项目的代码、整段对话历史、所有可能用到的工具。上下文窗口是稀缺资源，塞满的结果是信号被噪声淹没，模型花在无关材料上的注意力收不回来。

与之配套的是一条压缩纪律。一段好的进度记录应该具体到下一步能做决策，例如：

> 入口已找到，三个调用方中两个已改，第三个仍依赖旧错误码；新增测试失败，原因尚未定位。

这比「已完成 80%，继续优化」有用得多。压缩上下文时守住同一条线：假设仍然是未验证的假设，不能在摘要里变成已经确认的事实。

压缩的时机也值得挑一下。等到窗口快满再压，压的是半截推理；在一个阶段结束、结论稳定下来的时候压，沉淀下来的才是能复用的东西。前者省钱，后者省返工。

## 哪些步骤写死，哪些交给模型判断

「改代码之前先找调用方」「改完运行相关测试」这类步骤可以预先确定。具体要看哪些文件、测试为什么失败、旧接口怎么兼容，得根据现场反馈判断。

Anthropic 在 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 中区分了预设流程的 workflow 与由模型动态决定过程的 agent。这个区分对设计任务很实用：对执行顺序有把握的部分，交给程序和明确步骤；确实依赖现场信息的部分，再留给模型。

![固定流程、流程内模型决策和自主工具循环三种控制方式的取舍](/images/blog/diagrams/ai-agent-harness-engineering-01-control.svg)

两种极端各有各的代价。全部写死的一侧可预测、可审计、容易调试，代价是碰到没枚举到的输入就走不下去；完全放开的一侧灵活、应对意外情况的能力强，代价是难调试、难估预算，同一类任务跑两次的路径可能完全不同。

中间那一档往往最实用：外层骨架固定，比如「理解 → 修改 → 验证」三个阶段顺序不变；每个阶段内部看哪些文件、跑哪些测试，由模型自己决定。LangGraph 的 StateGraph 正好表达这种结构——图定义骨架，节点里可以再嵌一个子 Agent。

把每个分支都交给模型判断，是这类系统里最常见的过度设计；反过来，把所有可能情况预先写死，流程遇到没预料到的错误就没有退路。边界可以落在「每个阶段必须交出什么证据」上——规定清楚产出，比规定每一步调用哪个工具留出的空间更大。

接口迁移的阶段交付就可以是：理解阶段给出调用关系和不兼容点；修改阶段提交有限范围的差异；验证阶段运行检查并记录结果。新证据推翻原计划时，允许调整，同时保留调整原因。

## 计划要能执行，也要能被推翻

复杂任务先有计划，能帮助发现依赖和遗漏。计划写得长，不等于任务拆得好。「实现退款功能」太大；「读取第一个文件、读取第二个文件」又太碎，把探索过程误当成了承诺。

笔者更愿意按可检查的结果来划分：确定退款额度的不变量、增加并发用例、实现原子更新、验证旧接口兼容性。每一项都有输入和结束条件，失败时能判断是方案有问题，还是实现没做好。

动手之前还有一步常被跳过：让模型把需求反问清楚。真实需求通常比它听起来含糊，比如「退款要防重复」背后可能是「同一个幂等键只能成功一次」，也可能是「同一笔订单在额度内可以多次部分退款」。这两种理解会导出完全不同的实现，早一步问清楚比事后返工便宜。

把澄清、规划、执行、汇总这四步串起来，就是常说的 plan-then-execute：先问清楚目标，再产出任务列表，然后逐项执行并更新状态，最后检查是不是都达成了。Claude Code 里的 TodoWrite 就是这套东西的显式版本——它看着像个进度条，实际是复杂任务不跑偏的那根绳。

计划可以是 Markdown，也可以是结构化数据。调度器需要自动处理依赖和状态时，结构化格式更方便：

```json
{
  "tasks": [
    { "id": "1", "content": "确认旧接口的不变量", "deps": [], "status": "pending" },
    { "id": "2", "content": "补并发提交相同幂等键的用例", "deps": ["1"], "status": "pending" },
    { "id": "3", "content": "迁移第一个调用方", "deps": ["1"], "status": "pending" }
  ]
}
```

这样一份计划不用每轮重新解析，可以渲染成进度，可以让没有依赖关系的任务并行跑，中断恢复时也能直接定位到某一项。人工参与的小任务用一张短清单就足够，格式的作用是支持协作和恢复，不必要求所有计划都转成 JSON。

真正要守住的是计划允许被推翻。验证结果和原计划冲突时，改计划比硬着头皮执行下去省事，但改动原因得留下来——否则下一次恢复时，手上是一张和现实对不上的清单。

## 验证失败之后，下一轮拿什么继续

Agent 说「测试通过」之前，需要真的运行测试。单独再请一个模型读一遍代码，也替代不了编译、执行和检查真实行为。

不同强度的检查能拦住不同的问题：

| 检查手段 | 能拦住什么 | 拦不住什么 |
| --- | --- | --- |
| 编译、运行测试 | 接口不匹配、行为回归 | 需求本身被理解错了 |
| 类型检查和 lint | 一部分静态可见的错误 | 运行期才暴露的问题 |
| Schema 校验 | 输出结构不对 | 结构对但内容错 |
| 另一个模型评分 | 明显的质量缺陷 | 两个模型共享的同一种误解 |
| 关键词匹配 | 交付物里漏写了关键内容 | 写了但写错 |

执行级的检查最可靠，因为它不依赖判断。测试写错的时候，执行结果再稳定，也只是稳定地验证了错误的要求。

落到每个子任务上，至少要配一个属于它自己的验证手段，失败时走「看错误 → 修正 → 重试」的循环。测试驱动开发（TDD，Test-Driven Development）是这件事最自然的形态：测试就是需求的可执行版本，先红后绿再重构的节奏，和 Agent 一轮一轮干活的方式天然对得上。

关键决策点值得多花一点计算：同一个问题采样多次取一致结果，或者让两个模型互相挑错，都能提高单轮的判断质量。这类做法改善的是「这一轮想得对不对」，替代不了「产物到底行不行」——最后仍要落到可执行的检查上。

![任务执行后先做可执行检查，再审查需求覆盖；失败携带证据返回，超出边界则停止](/images/blog/diagrams/ai-agent-harness-engineering-02-verification.svg)

失败反馈至少要包含实际命令、错误输出和对应要求。例如：

```text
要求：重复提交同一退款请求，只产生一笔退款。
检查：并发提交相同幂等键的请求。
实际：响应返回了两个不同的 refund_id。
待查：幂等键唯一约束、事务范围，以及插入冲突后的返回逻辑。
```

最后一行是排查方向，不能冒充已经证实的根因。这样的反馈让下一轮有明确目标；只说「质量不够，请继续优化」，容易让模型在已经正确的地方反复改写。

独立审查者可以补充视角，但两个 Agent 仍可能共享同一种误解。给审查者原始需求、实际差异和验证结果，比只让它阅读实现者的总结更有用。

## 能恢复的状态，必须对应真实产物

上下文窗口之外还要有记忆，而且不止一层。当前任务的近期消息是工作记忆，通常靠滑动窗口保留；历史任务的摘要和关键事实是情景记忆，靠压缩后的文档传递；长期知识是语义记忆，放进向量库按需检索。三层压成一层，结果要么窗口很快撑满，要么跨会话什么都接不上。

状态本身也要分层。任务级记录每个子任务的 status、产物和错误；步级记录每次模型调用的输入输出、token 和耗时；事件级记录每次工具调用的参数、返回和耗时；会话级保存全局信息。分层的好处是可观测：出问题时能放大到任意一层，而不是只剩一句「任务失败」。

有个很好用的自检标准：把状态打印出来，一个新加入的人能不能看懂「现在在干什么、干到哪一步」。

恢复分三种情况。程序崩了，靠 checkpointer 把状态存进 Redis 或 Postgres，重启后加载；人工介入暂停，靠 `interrupt()` 和 `resume` 接上；跨天任务，每完成一个子任务就持久化一次，避免重做。

「步骤已完成」的记录和实际写入之间存在时间差。文件已经改了，进度还没保存就崩了——恢复时如果只认进度文件，这一段就会被重做。多花一次检查真实产物的代价，比覆盖掉已经做对的工作低。

带外部副作用的步骤更麻烦：PR 可能已经创建，只是返回结果丢了；通知可能已经发出，重试就会重复发送。这类操作需要幂等键，或者一个能查询的结果标识，不能只依赖 Agent 记得自己做过什么。

恢复还要考虑环境变化。记录的是昨天的测试结果，代码已经被别人改过，那份结果不能继续证明今天的产物正确。状态里至少要能对上是哪一份代码、哪一个产物。

一份能撑住中断恢复的状态大概是这样：

```json
{
  "task": "migrate-legacy-error-codes",
  "revision": "9f3c1ab",
  "subtasks": [
    {"id": "2", "status": "done", "artifact": "caller_a.go"},
    {"id": "3", "status": "done", "artifact": "caller_b.go"},
    {"id": "5", "status": "blocked", "reason": "caller_c 仍依赖旧错误码"}
  ],
  "next": "为 caller_c 加一层旧错误码映射，并补兼容测试",
  "budget": {"steps_used": 41, "steps_limit": 60}
}
```

字段不多，但每一类都在回答一个恢复时一定会问的问题：改的是哪个版本、做到哪了、卡在哪、下一步是什么、还剩多少额度。

## 循环停在哪里

有些失败值得重试：网络暂时不可用、依赖还没就绪。有些失败需要换方案：反复修改之后，测试仍然指向同一个错误假设。有些只能停下来：缺少凭据、需求互相冲突、下一步超出授权。

除了成功条件，还要在三个方向设上限：token 预算，累计超过就强制压缩或放弃；步数预算，最多循环多少次，对应 LangGraph 的 `recursionLimit`；墙钟预算，到点就走降级路径，实现上一般是一个 abort signal。任何一项超限，输出的是部分交付、一份明确的未完成说明，或者转交人工——继续跑下去只是把超支往后推。

「没有取得新进展」也需要一个明确判断。比较可靠的做法是让模型没法自己给自己松绑：不允许通过缩小测试范围、改掉断言、重新解释目标来换取通过。前两条容易发现，第三条最难——目标被重新解释之后，测试可能仍然是绿的。

反过来，预算也不是一味地省。前面提到的多次采样和交叉挑错，本质上是在关键决策点上主动多花一点。省和花的分界线，应该是「这一步判断错了，后面要返工多少」。

预算到了才叫停，通常已经晚了——那时候额度刚好烧完，手上只剩一份半成品。更实用的做法是在预算里留一条降级阶梯：消耗过半时减少并行度，或者把一部分步骤换给更便宜的模型；接近上限时收缩任务范围，只交付已经验证通过的部分；真正触顶时才停，同时把「还剩什么没做」写清楚。降级动作本身也要记进状态，否则下一轮会以为这些工作从来没有开始过。

错误的处理方式也分层次。最初级的 harness 遇到错误就重试同一个操作；好一点的会换个参数重试；真正有用的是把错误详情结构化地喂回下一轮，让模型看着失败现场重新决定下一步。

## 工具怎么给，记录留什么

工具设计上有几个具体现象值得注意：工具一多，每个 turn 都要过一遍选择，注意力被稀释；`read_file` 和 `load_file` 这类相似工具容易选错；描述之间还会互相干扰，A 的说明里恰好包含了 B 的触发词。常见的经验做法是把单个 Agent 绑定的工具控制在十个上下，相似能力合并，工具集很大时改成多 Agent 路由——由一个调度 Agent 决定交给哪个子 Agent，每个子 Agent 只带自己需要的那几个。

工具少不一定更好。把读、写、删塞进一个模糊接口，权限会变得很难控制，出错时也看不出到底是哪一步越了界。比数量更有用的标准是三条：当前任务需要哪些能力、哪些动作必须受限、结果能不能被检查。

「必须受限」这条展开来是有层次的：读文件可以放开，写文件要限定目录，执行命令和访问网络单独列出来按需授权，删数据、改配置、发外部消息这类不可逆动作默认拒绝。默认允许再逐个收窄，和默认拒绝再逐个放开，两者在出事故时的表现差得很远。

最后是运行记录。生产环境里的 Agent 从第一天就该接上链路追踪（tracing），不然「它为什么给出这个答案」这个问题永远答不上来。方案上，LangChain 家族可以用 LangSmith，想跨技术栈就用 OpenTelemetry 接进现有的 Grafana 或 Datadog，最低限度也要有自己的事件日志——每行一个 JSON 事件就够开始，字段大概长这样：

```json
{"ts":"2025-11-26T09:12:03Z","task":"migrate-caller-2","step":7,"tool":"run_tests","args":{"suite":"refund"},"exit_code":1,"elapsed_ms":8421}
```

至少要记下这些东西：每次模型调用的输入、token 数和耗时；每次工具调用的参数、返回和耗时；每个子任务的开始、完成和失败；用了哪个版本的输入、改了哪些产物、检查结果如何、为什么停下。越到后面越重要——出问题时，这些记录应该足以复原决策过程，不至于只剩一句「模型当时怎么想的，只有它自己知道」。敏感内容按需脱敏，并限制留存时间。

## 把这条链路走一遍

前面几节拆开讲的东西，串起来大概是这样一个流程。以接口迁移为例：

1. 澄清。先把「迁移到新写法」问具体：旧错误码是彻底删掉还是保留映射？兼容期多久？三个调用方是不是都要一起改？
2. 规划。按可检查的结果拆成几条——确认不变量、补并发用例、改第一个调用方、改第二个调用方、处理第三个的旧错误码。每条写清输入和结束条件。
3. 执行。模型自己决定读哪些文件、跑哪些测试；每完成一条就更新状态，记下产物位置和用到的代码版本。
4. 验证。跑类型检查和相关测试，再把原始需求、实际差异和验证结果交给一个独立审查者，看需求覆盖有没有漏。
5. 改计划。第三个调用方依赖旧错误码，直改会破坏另一条链路。计划被推翻，换成先加一层映射，把这个决定和原因写进状态。
6. 停下。墙钟预算快到，还有一条测试没跑通。循环停下来，交出的是「前两个调用方已改并有测试覆盖，第三个走了兼容映射，这条测试的真实输出如下」。

这六步里，只有第 3 步是模型在自由发挥，其余五步都在做工程。这也解释了为什么把模型接进真实链路之后，工程量反而是增加的。

## 停在这里不算失败

一个长任务能安全地停在「这里还没解决」，往往比它勉强给出一份完成报告更有价值。至少接手的人知道该从哪里继续。

接着上面那个例子往下看：这次迁移大概率没有全部做完，这没关系。重要的是它停下时，调用关系是完整的，两个已改的调用方有测试撑着，第三个没改的原因写在状态里，失败的那条测试带着真实输出。下一个人，或者下一轮，可以从这些材料接着走，不必从头再把旧模块读一遍。

把一次任务跑稳，和让这类任务每天自己跑起来，是两件不同的事：前者的问题在链路内部，后者的问题出在链路之间——谁负责发现新工作、同一个问题怎么避免重复处理、跑到什么程度算够。后一半是另一个题目，笔者打算另写一篇来算这笔账。

至于多 Agent 之间的分工该细到什么程度，笔者自己还没有稳定答案。现在的做法是先让单个 Agent 把一条链路走完，再考虑拆——这个坑先留着。
