设想两个节点都保存一个值 `x = 0`，彼此暂时无法通信。客户端向左边写入 `x = 1`，已经收到成功；另一个客户端随后去右边读取。右边不知道那次写入，它该返回什么？

返回旧值，会破坏这里要求的一致性；等到知道最新结果再返回，又无法保证分区持续时请求仍能完成。CAP 的矛盾就落在这两次操作上，用不着先把整个系统贴成 CP 或 AP。

摆在左边那个节点面前的路其实只有两条。第一条是这次写入先不返回，等联系上右边、把 `x = 1` 同步过去，再告诉客户端成功——网络一直不通，这次写就一直不成，客户端要么超时要么报错。第二条是左边直接返回成功，右边继续拿 `x = 0` 服务读请求——同一个键在两个地方有了两个答案，而两个客户端都以为自己看到的是唯一的那份。

笔者做稳定性治理这些年，方案评审里最常听到的一句是「我们这个系统到底是 CP 还是 AP」。每次听到都想先反问回去：说的是哪个操作？把上面两条路摆出来就会发现，这个问法丢掉了最关键的信息——`x` 到底是什么，读它的那次请求要拿去做什么。如果 `x` 是群公告的版本号，右边返回旧的顶多让人多刷一次；如果 `x` 是「这张券还剩几张」，右边返回旧的就可能让两个人买到同一张。

## 先对齐 C 和 A 的含义

CAP 里的 C 通常指原子一致性（atomic consistency），也就是线性一致性（linearizability）：并发执行的读写看起来像按某个顺序作用在同一个副本上，并且这个顺序尊重已经完成操作的先后关系。

「尊重已经完成的先后关系」听着抽象，落到界面上就是一句话：一次写入返回成功之后，后面任何一次读都必须看到这个值，或者比它更新的值。用户在设置页把昵称改掉、接口回了成功，跳回列表页却还是旧昵称——这中间可以没有任何故障，但只要它发生过一次，用户就不会再相信那个「保存成功」。

这种违反在分布式系统里有个更常见的来源：读写分离。写走主库、读走从库，从库靠回放 binlog 追上主库，而回放总有延迟。于是「下单成功，跳到订单列表却看不到这笔订单」会周期性地出现，两次请求其实都成功了，只是第二次读到了一个落后的副本。运维上常见的处理是让写完之后的一段时间内强制读主库，本质上就是承认这段延迟存在，再在需要它的那几个调用点上把它补回来。

A 的要求是：每个非故障节点收到的请求，最终都能得到一个符合操作语义的响应。这里有两个限定词值得逐字看。「非故障节点」把节点自己宕机排除在定理之外；「符合操作语义」意味着始终返回一句错误不算数，那只是把请求原地弹回去，并没有完成它。

它也不等于监控面板上那个月度可用率。后者是统计口径，前者是对单次请求的承诺：分区还在的时候，这一次请求能不能拿到一个有效结果。

P 是分区容错（partition tolerance），准确含义是节点之间的消息允许丢失、允许任意延迟，系统在这个网络模型下仍然要满足上面那两条性质。它描述的是故障模型，跟「我们部署在多个机房」是两回事——多机房只说明分区会发生，不说明系统对它做了什么。

分区和节点宕机是两种不同的故障，处理方式也不同。一个节点进程挂掉，集群知道它不在了，剩下的节点照常凑多数派；网络把节点隔开的时候，被隔开的那一个自己并不知道，它还会继续接受请求、继续对外声称自己是集群的一部分。多数派协议之所以要费劲区分这两种情况，就是因为后者会同时产生两个都自认为正常的视图。

单机系统里没有这个问题。一台 MySQL 实例配一份备份，事务的原子性、一致性、隔离性、持久性都在同一个进程和同一块盘上完成，不存在两个节点商量不拢的时刻。它并没有被排除在 CAP 之外，只是根本没有 P 这个维度。

所以「P 躲不掉，所以 CA 是伪命题」这句流传很广的话得改一改。准确的说法是：只要把数据放在两个可能失联的节点上，跨节点就已经是前提，CA 在这个前提下不在选项里；而要不要跨，是另一个得先回答的问题。单机 ACID 和分布式摆在一起比，比的是两件事——前者保证一个事务要么全成要么全不成，后者还得额外回答「两个节点联系不上的时候，这次请求怎么办」。

在这样的故障模型下，C 和 A 无法同时保证。[Gilbert 与 Lynch 的论文](https://www.cs.princeton.edu/courses/archive/spr22/cos418/papers/cap.pdf)给出的是形式化证明，而定理里的「最终」没有规定毫秒数。一个请求在分区期间挂 30 秒再返回，在定理的模型里仍算得到了响应；在收银台前排队的那个人那里，早就不算了。所以落回实现层，延迟上限得自己定，超时之后返回什么也得自己定。

## 选择一致性，不是让所有节点都停机

用共识算法（consensus algorithm）的系统——Paxos、Raft 都属于这一类——遇到分区时，能凑齐多数派的那一侧可以继续选主、继续提交，少数派那一侧无法确认新的写入。所谓「网络一断，整个集群停下来等恢复」，只在分区恰好把多数派也切开、或者集群本身只有两个节点的时候才成立。

多数派按节点数算，不按机房数算，这笔账得在选部署拓扑的时候就定下来。5 个副本如果 3 个放在 A 机房、2 个放在 B 机房，A 整个断掉之后只剩 2 个，凑不够 3 票，两边谁也提交不了；换成 2、2、1 分布在三个机房，断掉任意一个机房都还剩 3 个，集群照常服务。同样三个机房、同样五个副本，只是摆放位置不同，可用性就不是一回事。

少数派那一侧也不是什么都没发生。被隔离但进程还活着的节点，从调用方看和宕机差不多：请求要么被直接拒绝，要么一直挂到超时。麻烦出现在恢复之后——它手里的数据可能已经过期，得先把落后的日志追平再对外服务，而积压多的时候，这段追平时间会比分区本身还长。

还有一种做法是让少数派那一侧继续提供只读，理由是「反正读不会改数据」。这个让步要看读出来的东西拿去干什么：如果只是展示，旧一点没关系；如果这次读的结果会决定下一步写什么，那它和被隔离前最后一次同步的状态绑在一起，和读到错误数据没有区别。风险高不高，取决于读的用途，不取决于读这个动作本身。

多数派这一侧继续服务，代价是每次提交都要过一轮网络往返。同机房内这一轮通常在毫秒以内，跨地域部署时就是几十毫秒，而这几十毫秒会直接加在接口响应时间上。分区还没发生，这笔账已经先付了。

容量上还有一个连带的账：分区发生时，多数派那一侧能接的流量本身就少了一部分节点的额度。如果平时按所有节点都在线来估容量，分区那一刻，剩下的一侧会在处理请求之前先被自己的流量打满，表现出来和分区没有关系——是排队、超时和线程池耗尽。

这里还有一个对客服和运维都更要紧的差别：超时和报错是两种完全不同的结果。明确返回「暂时不可用」，调用方知道这次没成，可以重试；一直挂到超时，调用方只知道结果未知——它可能成了，也可能没成，接下来做的每一个决定都带着这个不确定性。CP 系统在分区时选择拒绝，把不确定性换成了确定的失败，代价是这一次请求真的没完成。

ZooKeeper 和 etcd 是这类系统里最常见的两个，它们把自己定位成 CP：元数据、服务路由表、分布式锁放在里面，宁可短时间不可用，也不接受两个进程同时拿到同一把锁。原因不难理解——两边的业务代码都以为自己持锁，接下来会同时去改同一份数据，而且往往已经发出了外部动作（扣款、发货、调用第三方接口）。这类动作撤不回来，等分区恢复再对账也补不上。

锁这件事还有一个容易漏的地方：光在本地内存里记一个「我拿到了」不算持锁，判断「谁持有」的那份记录必须落在分区时不会两边都认的存储上。用 ZooKeeper 的临时顺序节点也好，用 etcd 的租约加版本号也好，前提都是那份记录本身满足 C；如果锁的状态也存在一个异步复制的库里，主从切换之后两个进程照样会各自以为自己拿到了。

反过来也要小心，别把 CP 这个标签贴到整个系统上。一个系统里真正放进 ZooKeeper 或 etcd 的，通常只有锁、配置和路由这类元数据；订单、消息、账务这些大头仍然在 MySQL 主从或者分片集群上，其中不少还是异步复制。异步复制意味着主库切走的时候，最后几条已经返回成功的写入可能没到从库。所以「我们用了 etcd，所以我们是 CP」这句话，只对存在 etcd 里的那一小块成立。

不过愿意为一致性付代价的操作，范围其实很窄。抢一把锁、分配一个唯一编号、扣掉最后一件库存，这些操作的答案必须唯一，多等一会儿也认；查一份商品介绍、拉一页历史消息，两边即使给出不同结果也不影响任何决定，让它们陪着一起等，只是把还能用的那一侧也白白搭进去。

## 同一个对象上，不同操作的承诺可以不一样

是否值得为了一致性去等，最终由业务约束决定。把「面向用户的业务系统承受不起 CP」当成结论，会漏掉一种很常见的做法：同一个系统、同一个对象，不同操作的承诺本来就可以分开写。

举个笔者熟的例子。群成员这个对象上，「读一份成员列表」和「改一次成员名单」是两件事：前者晚几秒拿到、少显示一个人，用户刷新一下也就过去了；后者如果被两个分区同时接受，恢复之后谁在群里就没有答案。分区期间，成员列表可以照旧返回一份可能落后的快照，加人和踢人则应该明确失败或者阻塞，而不是两边都答应下来等着事后吵。

![分区发生时，同一份数据上的四种操作分别会怎样](/images/blog/diagrams/ha-about-cap-01-operation-promises.svg)

图里那四行回答的其实是同一个问题：这次操作在分区期间返回什么。要给出一个必须唯一的结果，就只能落在多数派那一侧；只是读一份允许落后的内容，两侧都能凑合。把这张表对着一份接口清单逐行填一遍，很快会发现有些接口把两类操作塞进了同一句承诺里——比如一个「查询群详情」的接口，同时返回群公告和当前操作者的发言资格：公告允许旧一些，发言资格若要用于发送准入，就不能只凭旧快照放行，但对外只有一个 200。

还有一类拆分不那么直观：同一份数据的「内容」和「版本」可以有不同承诺。群公告的正文读到几秒前的版本无所谓，但拿它去覆盖写入就不行了。写入时不校验版本号的话，一个基于旧正文的修改会把别人刚提交的修改整段盖掉，而从写入方看，这次操作完全成功。

同一个接口内部也还能再拆。发一条消息，「这条消息存在了」必须落在多数派那一侧，不能出现两个人对同一条消息存在与否给出不同答案；而同一时刻的未读数加一，晚几十毫秒到、或者由另一个消费者补上，通常没有影响。把这两件事绑进一次提交，代价是每次发消息都要等未读数那条路径；放开之后，未读数就变成一个需要自己保证「最终会追上」的东西。

账务上这个区别更明显。「查这笔订单扣了多少钱」读到略旧的结果，页面上晚几秒跳数字没人受伤；「这笔余额够不够扣」读到的必须是此刻的值，否则同一笔钱会被算进两次支出。这两个判断经常写在同一个服务里，甚至读同一行记录，但它们在分区期间能接受的东西完全不同。

这种「先把系统拆成一个个操作，再看每个操作要什么」的视角，和建模时区分用例其实是同一件事——换个场景，又会绕回来一次。

拆开之后，「能不能返回旧值」就不再是立场问题，而是一份可以逐条核对的清单。这件事从缓存那一侧看还有另一半，打算另写一篇：逻辑过期可以拿旧值顶上，前提是业务上真的允许那个结果旧。

## 允许继续写，就要处理分歧

如果分区期间两侧都接受更新，恢复之后需要确定怎么合并。覆盖其中一份、两份都留着让业务去挑、还是把冲突记下来人工处理，都会影响用户已经看到的结果——而用户看到过的那个版本，是收不回来的。

合并规则越省事，丢东西丢得越安静。按时间戳「谁后写谁赢」是最常见的一种：两个人在两个分区里各改了一次群公告，恢复之后系统挑时间戳大的那个，另一个人的修改就没了，两边都没有收到过任何提示。想让这类丢失停下来，要么把冲突本身当成结果留着交给业务判断，要么从一开始就把修改设计成可以叠加的操作，而不是互相覆盖的一整块文本。

合并还有一个绕不过去的约束：分区恢复之后别急着让两侧同时对外服务。合并逻辑通常要先停下来，把差异算清楚，再决定怎么落；一边服务一边合并的时候，正在被合并的那条记录很可能又被人改了，算出来的差异到落库那一刻已经过期。

「最终一致」也不是把事件丢进消息队列就自动成立。事件可能重复、可能乱序，也可能一直投递失败，于是重复扣减和漏掉扣减会同时出现。要让系统真的收敛，得先回答三个问题：冲突按什么规则解、重试到什么时候放弃、漏掉的那条靠什么补。答不上来的那一段，就是分区期间真实的不一致窗口。

重复和丢失是两种不同的毛病，别指望一个手段同时治住。消息重复投递要靠接收侧的幂等键或者去重表挡住，做得不好就是多扣一次；消息彻底丢了，幂等写得再严密也变不出那条记录，只能靠对账或者定时扫描把差值找回来。一套系统里通常两套都有，各管一头。

修补的时机也有两种。趁读的时候顺手比一下各副本的版本、发现落后就补上，这类做法通常叫读修复（read repair）；后台另起一个任务定期扫两边的差异，一般叫反熵（anti-entropy）。前者只在被读到的那部分数据上生效，没人碰的冷数据可能一直不一致下去；后者覆盖得全，但慢。多数系统两套都要，原因就在这里。

冲突什么时候暴露给用户，也是一个要提前定的问题。写的时候就挡回去，用户当场知道「这份内容别人也在改」，代价是写入路径得能识别冲突；一直拖到读的时候才把两个版本摆出来，写入路径简单了，用户却可能过很久才发现自己的修改根本没生效。选哪一边，取决于这份数据是「两个人同时改的概率很低」，还是「本来就会撞」。

「最终一致」里的「最终」，还得有一个能观测到的收敛信号。对账差异条数归零、副本版本号追平、积压消息清空，这些都算；没有这个信号的时候，这句话就只是一句声明——真出了问题，连「现在到底一致了没有」都答不上来。

BASE 常被用来概括这类设计，三个词拆开看会具体很多：

| 要素 | 在系统里的具体表现 |
| --- | --- |
| 基本可用（Basically Available） | 分区期间允许损失一部分能力：降级、限流、转只读，核心链路继续响应 |
| 软状态（Soft state） | 允许存在中间状态，比如「支付中」「发货中」，不要求每个时刻各副本相同 |
| 最终一致（Eventually consistent） | 停止写入之后，经过一段同步时间，各副本收敛到同一份结果 |

「软状态」这个词最容易变成挡箭牌。接口回一句「处理中」，然后就没有下文了——状态停在处理中多久、谁来推进它、推进失败几次之后告警，这三件事没有答案的话，用户下次刷新看到的还是「处理中」，问题只是从一次同步调用变成了一行没人推进的记录。

## 别用 CAP 解释所有异步架构

Redis 预扣库存、再通过 MQ 把真正的扣减写进数据库，这个结构经常被直接当成 AP 的样板。但它更像是在做削峰、压低接口延迟或者划分业务阶段；只看这张结构图，判定不了它是 CP 还是 AP。

答案取决于谁说了算。如果 Redis 里的计数就是可售库存的权威，那这套系统的一致性上限由 Redis 自己的持久化和主从切换决定，数据库只是记账的副本——切主时丢掉的那几秒扣减，丢掉就是丢掉了，没有别的地方能还原。

如果数据库那一行才是权威，Redis 只是一道准入闸门，那 Redis 丢掉的扣减就会变成超卖：闸门放过去的比实际库存多。这种结构真正要回答的是，多放过去的那部分怎么收回来，通常落在对账和人工处理上。

如果两边都不算权威、另有一层以数据库最终结果为准的补偿，那这就是把一次同步事务拆成了两个阶段，代价是用户先拿到一个可能被推翻的「成功」。什么时候告诉他推翻了、用什么方式告诉他，是这套结构必须自己解决的问题。

消息队列在这套结构里既不提供一致性，也不破坏一致性。它做的事是把一次调用拆成两次，并让第二次可以重试。判断这套结构给出的是什么承诺，看的仍然是哪份数据说了算，中间多放几个组件并不改变这一点。

再往下说一层，削峰和一致性其实是两件事。前者解决的是「瞬时请求量超过下游处理能力」，和分区时选 C 还是 A 没有关系——一个系统完全可以既排队削峰又保持强一致，让每个扣减都在多数派上确认，只是每次都要慢一点。反过来说，异步落库也不等于放弃了唯一性判断：只要「能不能扣」这一步是原子的，落库慢一点并不会让两个人扣到同一件库存。

顺着这个例子还能分清另一处容易混的地方：ACID 里的 C 指的是事务执行前后约束不被破坏，和 CAP 里的 C 不是同一个定义。单机数据库一样有多种隔离级别，可重复读和读已提交给出的承诺就不一样——那个 C 管的是约束，不是「所有副本看起来像一份」。

同一个字母在两处意思不同，评审会上很容易变成一场误会。有人说「我们的账务要 ACID，所以是强一致」，听的人理解成「所有副本任何时刻完全一样」，两边其实在说不同的事，却会为了同一个词争上半小时。

把 ACID、CAP、BASE 排成一条「旧技术被新技术取代」的时间线，是最省事也最容易讲错的讲法。它们本来就不在同一个层面上：

- ACID 管一个事务之内的原子性与约束；
- CAP 管分区期间跨节点的读写承诺；
- BASE 管把一致性推迟之后，靠什么把系统收回来。

## 把承诺写成一张表

上面这些判断，落到方案评审里就是一张表。随便拿一个写操作来填，比如「用户提交一次群公告修改」：

| 要回答的问题 | 答不上来会怎样 |
| --- | --- |
| 这份数据存在哪些节点上，分区时哪一侧还能写？ | 恢复之后发现两边都改过，没人知道该听谁的 |
| 写入返回成功，承诺了什么？ | 调用方以为已经生效，实际可能被后面的合并盖掉 |
| 分区期间读这个对象，允许返回多旧的值？ | 降级只能凭感觉写，要么降太狠，要么把旧值当成新值用 |
| 不一致最长能持续多久，超了谁来兜底？ | 监控上看不出来，只能等用户来投诉 |
| 这次操作失败了，调用方怎么知道？ | 超时和报错被当成同一件事处理，一重试就多扣一次 |
| 两份更新撞上了，是丢弃、保留，还是交给业务判？ | 「谁后写谁赢」把其中一份改动静默地扔掉 |

一行一行填下来会发现，会上大部分争论其实是在争其中某一行，而那一行要的答案来自业务，不来自协议。协议能告诉你分区时会发生什么，告诉不了你这份数据能不能旧、能旧多久。

开头那两次操作真正逼着人回答的，不是「这个系统选哪一边」，而是「这一次读取，在分区期间应该返回什么」。笔者现在讨论方案的习惯是先把分区画出来，再逐个操作往下填：正常返回什么、超时返回什么、恢复之后要不要合并。填到哪一行卡住，那一行的代价就是这次真要付的。

没有分区的时候，同一组取舍换了个名字继续存在：一份跨节点写入，是等所有副本都确认再返回，还是先返回、承担一点不一致。Daniel Abadi 把这个扩展总结成 PACELC——分区（Partition）时在可用性和一致性之间选，否则（Else）在延迟和一致性之间选。它解释了一个挺常见的困惑：某个系统在健康状态下响应就偏慢，和它面对分区时的选择，往往是同一个决定的两面。

跨机房部署时那个读请求的延迟上限该定多少、超时之后返回什么，就落在这两条线上，是另一个话题，先挖个坑。
