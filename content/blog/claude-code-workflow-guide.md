笔者日常的主力工具就是 Claude Code 和 Codex，一天里相当一部分代码是从这两个终端里出来的。不过「在用」和「会用」之间隔了挺长一段时间：早期的用法基本是把它当成一个能读仓库的问答窗口——问一句，答一句，改一行，再看一眼。

真正的变化来自一个很朴素的转身：不再向它提问，而是向它交代任务。改哪一部分、哪些行为必须保留、用什么结果判断完成，这三件事说清楚了，它才有可能自己跑完一串工具调用，最后交回一份能验收的东西。

这篇只谈单次任务怎么推进：输入框里几种前缀分别会发生什么、每天真正用得上的命令、什么时候该先让它规划、以及怎么把它接进脚本。任务内部的上下文怎么组织、结果怎么验证、验证没过之后从哪接着跑，笔者上个月在[《Agent 长任务跑稳，靠的是上下文、验证与恢复》](/blog/ai-agent-harness-engineering)里写过一遍；项目规则和扩展机制准备另开两篇写。本机实际有哪些命令仍以 `/help` 为准。

## 四种前缀：同一句话，走不同的路

同一个输入框，行首那个字符决定了这句话接下来走哪条路：

| 输入 | 送达的位置 | 例子 |
|------|-----------|------|
| `/` | 斜杠命令。一部分直接改会话状态，一部分是 prompt 驱动的 Skill（按需加载的提示词模板） | `/clear`、`/compact`、`/review` |
| `@` | 文件或目录的内容被读进上下文 | `@src/server.ts`、`@docs/` |
| `!` | 先在本机 shell 执行，输出再进上下文 | `!git status`、`!pnpm test` |
| 普通文本 | 交给模型，由它决定接下来调用哪些工具 | 「检查支付回调的幂等处理，先只分析」 |

`!` 是本机先动手：shell 立刻执行，输出作为事实进上下文，模型不必先判断「这条命令要不要跑」。所以 `!git status` 比在提示词里写「帮我跑一下 git status」少一次工具调用的往返，拿到的东西一模一样；开头那个 `!` 是 Claude Code 的前缀，后面的内容一律按 shell 语法执行。更完整的按键与交互说明见[交互操作参考](https://code.claude.com/docs/en/interactive-mode)。

`@` 的作用是缩小定位范围。引用一个入口文件、再说明要追踪哪条调用链，通常比把整个源码目录塞进提示词更清楚。要注意目录引用不等于所有文件都已被完整读完，关键结论仍然要它给出代码位置。

还有一个不太被提起的 `#`：行首写 `# 这个仓库用 pnpm 而不是 npm`，这行字会被追加进 `CLAUDE.md`，之后的会话默认带着。写进去之前先分清它是团队约定还是个人偏好——这两类东西该放的位置不一样，分层的规则准备另开一篇细讲。

## 每天真正用到的命令其实就那么几条

按频次排，最高的是会话与上下文这一组：

| 命令 | 什么时候用 |
|------|-----------|
| `/clear`（别名 `/reset`、`/new`） | 换任务之前，清空上下文但保留 `CLAUDE.md` 这类项目记忆 |
| `/compact` | 任务还要继续、上下文快满了，可以带上一句保留要求 |
| `/resume` | 跨天接着做同一件事，翻出历史会话 |
| `/branch` | 从当前对话分叉，同一件事试两种约束 |
| `/rewind` | 回退本轮，可选只回退对话、只回退代码，或两者一起 |
| `/cost`、`/context` | 大改动前后各看一次，判断长日志和重复检索占了多少空间 |
| `/rename` | 给长任务起个名字，方便以后 `/resume` 找回来 |

同一个问题还在推进的时候，继续原会话更合适：已经确认的根因、被否掉的方案、后来补上的约束，都是后面还要用的上下文，没必要为了「干净」在每一步之前都 `/clear`。转去不相关的任务时再清，长任务中途则用 `/compact` 交代保留什么：

```text
/compact 保留支付回调的根因证据、已排除的假设、兼容约束和未完成验证
```

新仓库里第一条该跑的是 `/init`：它扫一遍仓库，生成一份 `CLAUDE.md` 草稿。草稿就是草稿，提交之前自己 review 一遍。之后想改就用 `/memory` 打开编辑视图，或者直接用上面那个 `#` 追加一行。另外别把 `-c`、`-r` 记成会话里的命令，它们是在 shell 里启动时用的 flag；会话里翻历史只有 `/resume`。

排查类命令用到的频次低，缺了却很难受：`/review` 让它在提交前自查改动，`/diff` 打开交互式 diff，`/permissions` 管哪些工具和哪些 shell 命令不用逐次批准，`/doctor` 诊断安装与配置。

近几个版本还多了一批长得和命令一样的 Skill：`/simplify` 在提交前找重复实现，`/security-review` 扫当前分支的安全问题，`/debug` 在卡住时打开调试日志，`/loop 5m` 反复跑同一个提示词盯 CI。它们是提示词模板而不是硬编码逻辑，行为会随版本漂移，用之前先 `/help` 确认当前版本里真的有。

几个不用敲命令的动作同样值得练熟。方向偏了立刻按 `Esc`，中断保留已经发生的工作，但不会自动撤销修改；输入为空时双击 `Esc` 打开 rewind 菜单，而 rewind 只覆盖它自己追踪的代码与会话状态——通过 shell 产生的改动、数据库写入、远端操作都不能指望它恢复，重要改动仍然要靠 Git diff、分支或 worktree。`Shift+Tab` 循环切换权限模式（permission mode），`Ctrl+B` 把长命令丢到后台再用 `/tasks` 看进度，多行提示词用 `\` 加 Enter（`Ctrl+J` 也可以），架构图和报错截图可以直接拖进终端。[检查点与回退](https://code.claude.com/docs/en/checkpointing)

这一堆动作里真正省时间的只有一个：`Esc`。等它跑完再纠正的代价，通常比当场打断高一个量级。

## 上下文是一份预算

同一个会话里，每个动作都在往上下文里加东西或者减东西，方向记住就够用了：

| 动作 | 对上下文的影响 |
|------|--------------|
| 换任务时 `/clear` | 释放掉大部分占用 |
| `@` 一整个目录 | 占用很大，尤其是不清楚目录里有什么的时候 |
| 把长日志直接粘进提示词 | 占用很大，先落地成文件再 `@` 更划算 |
| 让子代理（subagent）翻文件、只回摘要 | 占用很小，代价是要多组织一次任务 |
| `!` 跑一条命令 | 占用小到中等，取决于输出有多长 |
| `/effort` 往上调一档 | 思考部分变多，账单跟着一起走 |

三条经验可以先记住：换任务必清、大范围探索交给子代理、大文件先 grep 再读。

子代理那条的收益最容易被低估：它翻五十个文件、只把结论带回来，主会话省下的不只是五十份正文的 token，还有被这些正文稀释掉的注意力。至于「先 grep 再读」，前提是你大概知道要找的东西在哪；连位置都不知道的时候，让子代理先去摸一遍比省 token 更要紧。

预算要看得见才管得住：`/cost`、`/context` 回答的是「空间被什么占掉了」；给每一次任务都记一笔账，是另一件事。

## 模型和推理强度，先沿用默认值

普通实现先用当前可用的默认模型。遇到跨模块行为、并发时序、难以区分的根因，再考虑换模型或者提高 effort；判断标准只有一条——更充分的分析能不能消掉一个具体的不确定性。任务标题里写着「架构」两个字，不算理由。

三档分工大致是稳定的，本机具体有哪些型号看 `/model` 列表：最强的那档留给架构判断和难 bug 归因，中间档跑日常实现、重构和测试，最便宜的那档做批量格式化、日志解析这类不需要判断的活。有的版本还把「计划阶段用强模型、Accept 之后自动切回中档」做成了配置项，名字叫 `opusplan`；本机没有这一项，就在进 plan 前手动 `/model opus`、Accept 之后再切回去。

`/effort` 调的是任务级的努力档，档位名、可用范围和默认值都随模型变化。照抄旧教程里的固定组合，很容易配出一个自己都不认识的默认值。

思考深度还有一套写在提示词里的老办法：在任务描述里塞 `think`、`think hard`、`ultrathink` 这些词。这里要纠正一个流传很广的说法——把 `think` 当成 4K token、`think hard` 当成 10K、`ultrathink` 当成 32K 的那张对照表，不能再当配置说明用了。按当前文档的说法，这些短语按普通文本处理；`ultrathink` 增加的是「这一轮深入推理」的指令，并不会改变发给 API 的 effort 值。

`/fast` 也容易被读成省钱开关。它给的是更快的响应，走的是更高费率，适合在确实在意交互延迟的时候评估，不适合因为「任务简单」就默认打开。[模型与 effort 配置](https://code.claude.com/docs/en/model-config)、[Fast mode](https://code.claude.com/docs/en/fast-mode)

## 先规划还是直接改

需求还没定型、改动会影响线上行为、几种实现方式的取舍都摆在明面上时，先让它规划。进入方式有几种：`Shift+Tab` 循环到 plan 最顺手，切完看一眼界面提示，确认真的停在 plan 上；`/plan [任务描述]` 可以顺手把任务带上；启动时 `claude --permission-mode plan` 直接以计划模式开会话；想让它成为默认，就在 settings 里设 `defaultMode`。权限模式的档位和可用项随版本、组织配置变化，不必去背固定档数。

进了 plan 之后，它只能调用 Read、Grep、Glob 这类只读工具，产出一份实施计划；你 review 完、把方向纠回来，点 Accept plan 才会真的开始改代码。

![直接改与先规划两条路径的纠错点对比：直接改在 diff 之后纠错，先规划在动手之前纠错](/images/blog/diagrams/claude-code-workflow-guide-01-plan-vs-direct.svg)

计划最该回答三个问题：现状在哪个文件里实现，改动会影响哪些调用方，怎么验证兼容性。只有目录清单和「编写测试」四个字的计划，通常说明关键问题还没浮出来。

四类任务值得每次都走一遍：涉及三个以上文件或跨模块的改动、有架构选型空间的、你自己也没完全想清楚的、对生产行为有影响的（迁移、回滚、表结构变更）。反面同样清楚——已经定位到一个字段名写错、影响范围明确，直接授权修复并验证就好，不必再开一轮方案评审。

「给接口加缓存」是典型的分水岭。缓存键用什么、什么条件下失效、允许多旧的数据，这三个问题答完，放 Redis 还是放进程内基本就自己定下来了；一上来就让它动手，拿到的往往是一个能跑、但没有失效策略的缓存。[Plan 模式用法](https://code.claude.com/docs/en/common-workflows)

## 一天跑下来大概是什么节奏

实现新需求时，笔者这边的顺序大致是这样：

```text
1. /clear                      换一个干净的上下文
2. 描述需求 + @相关目录 + "进 plan 模式"
3. 计划出来，自己 review、纠偏、补充约束
4. Accept plan，开始执行
5. 跑偏了立刻 Esc；缺文档就 @具体文件 追加
6. /review 自查一遍
7. !pnpm test && pnpm lint     验证走本机 shell，输出直接进上下文
8. 让它在 diff 基础上写一份 commit message 草稿
9. 看一眼 /cost，然后 /clear 准备下一个任务
```

查 bug 是另一套节奏，关键在把假设和验证分成两段：

```text
1. /clear
2. 贴报错日志 + 复现步骤 + "先只分析，不要改代码"
3. 它给出若干根因假设，以及每个假设怎么验证
4. 挑最有区分度的那条：按假设 2 继续，可以读代码、跑测试，先不要改
5. 根因确认之后再动手：按最小改动修复，带上能重现原问题的测试
6. /review → 验证 → 提交
```

两段式的好处是纠错便宜。假设阶段全是只读操作，方向错了只损失几分钟阅读时间；等它按错误的根因改完一大片再回退，代价完全不是一个量级。这里也别硬要求它每次都凑出三个根因——凑数的那两个通常是噪声，只读的检索步骤也不必每一步都回来请示。

手里的活不止一件时，可以用 git worktree 把并行摊开：每个任务一个工作目录、一个会话，上下文互不干扰，正跑着重构时来人报 P0，在新目录里开会话就好，前一个不用打断。有的版本把这步收进了命令，`claude -w <name>` 直接在仓库的 worktree 目录里起会话，加 `--tmux` 还会顺手开面板。真要一次改几十个包，还有 `/batch` 这种派多个 worktree 子代理并行开工的 Skill——省时间，但 token 是按份数烧的，动手前先算一下值不值。

## 把任务推进到可以检查的结果

任务说明写得好不好，直接决定要不要返工。一个能用的版本大概长这样：

> 为 billing 的退款接口补幂等处理。先读现有支付回调和退款测试，保持公开 API 不变。说明重复请求和网关超时后重试分别怎么处理，再按最小改动实现，最后给出实际运行过的验证结果。

它交代了三件事：范围（退款接口、公开 API 不变）、约束（重复请求与超时重试）、验收方式（实际运行过的验证结果）。少写哪一条，它都会自己补一个默认答案，而默认答案大概率不是你想要的。

约束还有一种更省事的给法：不描述规则，直接引用一个做对了的例子。「参考 `@src/modules/order/OrderService.ts` 的结构、命名、错误处理和日志粒度，给 PaymentService 做一次同风格重构」——模仿现成代码的准确度，通常高于照着一段自然语言规范去写。

执行过程中要时不时看一眼它读的代码对不对。缺少网关契约就补契约，误解了状态含义就当场纠正，不必等它写完再从头来过。改完先看 diff：有没有顺手重命名、把异常捕获范围放大、升级依赖、或者把跑不过的测试改掉——这几类变化都需要单独的理由。

收尾报告至少要分清三件事：改了什么、实际执行了什么、什么还没验证。「建议运行测试」不能当成「测试通过」汇报上去。让它写一份 commit message 草稿没问题，但真正执行 commit、push 是另一个动作，需要单独授权——这两件事在终端里只差一个回车，在责任上差着一个人。

## 非交互运行：把它接进脚本

`claude -p` 以非交互方式（headless）跑，适合 CI、cron、pre-commit 钩子这类场景。落到流水线里通常是几件事：PR 每次更新跑一遍 review、每天扫一次新合入的代码、新 issue 进来先定位可能涉及的模块。下面这条在仓库里检查未提交的 diff：

```bash
claude -p "读取当前 git diff，检查是否引入 N+1 查询；只报告有代码依据的问题，不修改文件" \
  --tools "Read,Grep,Glob,Bash" \
  --allowedTools "Read,Grep,Glob,Bash(git diff *)" \
  --max-turns 5
```

这里有两组容易混的参数：`--tools` 控制这次会话能用哪些工具，`--allowedTools` 控制哪些调用不必逐次批准。前者是能力边界，后者是审批边界，互相替代不了。

把预算和输出格式也钉住，下游脚本才好接：

```bash
claude -p "扫描最近 24 小时的提交，找出与 CLAUDE.md 约定不一致的地方" \
  --allowedTools "Read,Grep,Glob,Bash(git log *)" \
  --max-turns 10 \
  --max-budget-usd 2.00 \
  --output-format json
```

`--output-format` 有三种：`text` 给人看，`json` 一次性返回整段结果、方便脚本解析，`stream-json` 适合长任务或者需要边跑边消费事件流。要下游严格按结构解析，还可以加 `--json-schema` 指定 schema；只想跳过 hooks、skills、MCP 这些扩展、让脚本跑得快一点，用 `claude --bare -p`。数小时的活，比如全模块的 lint 清理，可以 `claude --remote` 丢到云端 sandbox 跑，不占本机。[CLI reference](https://code.claude.com/docs/en/cli-reference)

轮数上限只是约束循环，它替代不了文件权限、网络限制和 CI 凭据隔离。`--allowedTools` 给到 `Read,Grep,Glob,Bash(git log *)` 这种程度，读得到的东西仍然很多，上面这些示例也不该直接当成不受信任仓库的完整隔离方案。接进 CI 之前，先在临时仓库把输出格式和退出状态验一遍，别等流水线红了才发现解析不了。

还有一条底线：模型的审查结论是给人做定位参考的，已有的测试、静态检查和发布权限仍然由原来的工程流程负责。它说「没问题」不等于没问题，它说「有问题」也需要人确认一遍再动手。

回到开头那个转身：把任务交代清楚，比把问题描述漂亮更重要。上面这些命令里，真正让笔者少返工的只有两条——`@` 一个准确的入口，和一句「先只分析，不要改代码」。

权限模式里还有几档笔者没在日常任务里跑过，等碰上真实场景再回来补记录。至于它为什么能干这些活、还能接什么——Skill、MCP、Hook 和子代理怎么分工，准备另开一篇写。
