「每天检查 CI 失败，能修的修掉，留下 PR 给我看。」这个要求比「修复眼前这条报错」多了几件事：谁来发现新工作，同一个失败会不会重复处理，修到什么程度可以交付，下次运行怎样接上进度。

这正是 Loop Engineering 讨论的问题。[Addy Osmani 的文章](https://addyosmani.com/blog/loop-engineering/)把它描述为：由系统持续发现、分派、检查和记录工作，减少人逐轮发出指令的需要。他列出了调度、worktree、skills、连接器、子 Agent 和外部状态等构件。这是一种组织工作的思路，不是一套必须配齐的产品清单。

这篇来填一个很久之前留下的坑。八个多月前那篇[Agent 长任务跑稳，靠的是上下文、验证与恢复](/blog/ai-agent-harness-engineering)关心的是链路内部——一次任务怎样跑稳；链路之间的事，它留在了结尾。这里再向外看一层：任务反复运行以后，哪些问题会变得重要。

先坦白一句：这一篇是这个系列里笔者最没底的一篇。一次任务内部的那些事，笔者踩过坑也总结得出几句；真正长期无人值守跑着的系统，笔者并没有做过。下面写的是设计推演，以及从公开材料里读到的具体做法。哪些是笔者想清楚了的、哪些只是推演，尽量分开说。

还有个客观限制：这个概念在公开讨论里出现得很晚，能看到的一手材料大多是产品团队在介绍自己的做法，横向可比、带量化结果的第三方数据几乎没有。所以下面出现的具体数字都是示例阈值，不是实测结论。

## 定时运行，只解决了启动问题

给一个脚本加 cron，很容易让它每天开始。要让它每天做对事情，还需要定义输入范围和状态。

以 CI 修复为例，同一个失败可能出现在多个 job 里，也可能连续几天都没解决。发现它以后，要先判断是否已经有修复任务、相关代码有没有变化、失败是不是外部服务暂时不可用。否则调度越勤，重复任务越多。

启动信号其实有四类，各自带回来的信息很不一样：

- 定时触发。cron 到点就跑，输入只有时间。它适合例行巡检，不适合救火——周一挂掉的 job，周三早上才会被看到。
- 事件触发。代码推送到主干、CI 失败、新 issue 打开，这类 webhook 把上下文一起送过来：哪个提交、哪个 job、哪一步失败。响应快，代价是同一个提交触发多条事件时容易重复开工。
- 条件触发。积压超过阈值、某个 job 连续三次失败、失败率高于上周同期。输入是统计结果，反馈是「情况在变坏」。它依赖一份可信的计数，计数不准就会来回抖。
- 人工触发。有人在 triage inbox 里挑一条丢进来。输入是人的判断，最贵也最准；前三类处理不了的，最后都落到这里。

这四类不是四选一。一个能用的循环通常以定时打底，用事件做快速通道，靠条件决定要不要升级，把人工留在最后兜底。

Addy 列的那几个构件，可以按「缺了它会怎样」来看：

| 构件 | 作用 | 缺了它会怎样 |
| --- | --- | --- |
| 调度 automation | 按时间或事件启动循环 | 退化成一个一次性脚本，跑不跑看人记不记得 |
| 隔离目录 worktree | 给每个并行任务一份独立检出 | 多个 Agent 改同一个文件，冲突留给人工收拾 |
| 技能 skill | 把项目约定固化成可复用的说明 | 每一轮都从零推导你的项目该怎么写 |
| 连接器 connector | 让循环能开 PR、更新工单、发消息 | 活干完了停在本地，交付还得人搬 |
| 子 Agent sub-agent | 把制造者和检查者分开 | 写代码的给自己批作业 |
| 外部状态 memory | 记住做过什么、下一步是什么 | 每次运行都从零开始，重复劳动 |

其中「制造者和检查者分开」值得单说。人写代码都有自己看不出自己问题的时候，模型对自己产出的置信度还更高一些。所以一个靠谱的循环会派第二个 Agent 审第一个的产出，最好用不同的提示，甚至不同的模型。成熟的框架里常见一个独立的 goal-checker，配一个更小更便宜的模型，专门判断任务到底完成没有——也正因为要交给别人判断，停止条件必须写成可验证的表述，比如「退款模块的测试全过、lint 干净」，而不是让干活的模型自己说一句 done。

外部状态用 Markdown 文件或者看板这种土载体就够了，不必塞进上下文窗口。理由很实在：模型会忘，仓库不会忘。写在磁盘上的东西，下一轮读起来就能接着干。

worktree 处理的是代码隔离。两个 Agent 在不同目录修改，可以减少文件冲突，但可能同时改了同一个接口的语义。隔离目录没有消除集成和审查的工作，也没有解决共享数据库、端口等运行资源的冲突。

## 四种循环，对应四种反馈

前面说的是循环怎么被叫醒，这一节说的是被叫醒之后，一次反馈究竟改变了什么。LangChain 的 [The Art of Loop Engineering](https://www.langchain.com/blog/the-art-of-loop-engineering)把工作分成四层：工具调用、结果验证、事件触发，以及根据运行记录改进 harness。下图保留这层区分，便于看清一次反馈究竟改变了什么。

![从工具调用到验证、事件触发和配置改进的四层循环](/images/blog/diagrams/loop-engineering-01-loop-stack.svg)

最内层解决当前任务：读取文件、运行命令、根据输出再行动，它改变的是这一步做什么。验证层决定结果是否满足要求，失败时携带具体证据返回，它改变的是产物本身。事件层决定什么时候启动新的工作，它改变的是队列里有什么。配置改进层观察多次运行，提出对提示、工具描述或流程的修改，它改变的是下一次运行的规则。

四层的检查对象不能混在一起。代码测试通过，不能证明发现问题的规则没漏报；某次修改提示后得分提高，也不能证明它对所有任务都有帮助。

最外层尤其危险：如果让同一套系统同时改答案和改评分标准，就可能获得越来越好看的分数，却离原目标越来越远。笔者的做法是把评分基准和保留样本独立管理，配置变化先通过回归比较，再决定是否采用。生成改进建议是一回事，批准自己的新标准是另一回事。

第四层听起来最玄，最小可行形态其实不复杂：把第二层里评分偏低、却靠重试蒙混过关的用例单独收集起来，交给一个分析 Agent，让它去改评分用的 rubric 提示，或者调整某个工具的说明。改动本身仍要走一次回归比较，通过了才生效。再往前一步，就是拿运行记录直接去调模型权重，那已经不是应用工程能覆盖的范围了。

这四层里，真正拉开差距的是第二层和第三层，公开的落地经验也集中在这两层。最内层从 ReAct 那会儿就有了，第四层目前还停在少数团队的实验里，能看到的多是设想，带量化结果的案例很少。

## 把每天修 CI 的流程写具体

下面是一个设计示例，不是无人值守生产系统的实测记录。它把交付边界放在待审查的改动上，合并与发布仍由项目既有流程处理。

![从定时检查 CI 到去重、隔离修复、验证与人工审查的流程](/images/blog/diagrams/loop-engineering-02-ci-workflow.svg)

拆开来是这样九步：

1. 取清单。读最近一次主干构建的失败列表，每条带上工作流名、job 名、提交 SHA、失败步骤和错误摘要。缺了定位信息的条目，先补全再往下走。
2. 对历史。查这次失败对应的提交是不是已经有人开过修复 PR，是不是同一条错误昨天出现过。已经在处理的跳过，只留下真正新的。
3. 分诊。把失败分成三类：代码引起的、环境或外部依赖引起的、测试本身不稳定的。重跑一次仍然失败，且错误指向本次改动的文件，才归到第一类。
4. 建隔离环境。从主干切一份 worktree 或临时分支，装依赖、起服务。数据库、端口、缓存这些共享资源要么隔离，要么串行排队。
5. 先复现。改任何代码之前，先把同一条错误跑出来，并留下完整输出。复现不了的问题不做修复，退回分诊。
6. 再修。改动范围限制在与这次失败相关的文件里。顺手发现的其他问题单独记一条，不混进这个 PR。
7. 验证。跑失败的那个 job，再跑一遍受影响的测试集。绿灯必须来自和 CI 上同一条命令，不能是本地换了个更宽松的参数跑出来的。
8. 登记。把问题标识、提交 SHA、尝试过的改法、验证结果、产物地址写进外部状态，然后才创建 PR。
9. 交付。PR 描述里放四样东西：失败原因的证据、代码改动、验证结果、仍然不确定的地方。人看完决定合并还是打回。

第 8 步排在第 9 步前面是有意的。如果先创建 PR 再登记状态，中间崩溃就会留下一个没人认领的 PR，下一轮重新跑一遍同样的流程，还会再开一个。

外部状态里一条问题记录大概长这样：

```json
{
  "issue": "ci/flaky-refund-lock-test",
  "commit": "9f3c1ab",
  "attempts": [
    {"round": 1, "change": "扩大超时时间", "result": "仍然失败，错误签名相同"},
    {"round": 2, "change": "改成串行执行", "result": "仍然失败，错误签名相同"}
  ],
  "artifacts": ["branch:fix/refund-lock-test"],
  "next": "两次同因失败，转人工；超时与并发两个方向已排除",
  "budget_used": {"rounds": 2, "rounds_limit": 3}
}
```

字段不多，但它让第 2 步和第 3 步有据可查：下一轮读到「两次同因失败」，就不会再沿着同样的方向走一遍。

遇到网络抖动或测试本身不稳定，不能用删掉测试、放宽断言来换取绿灯——这类「修复」会让下一轮的判断建立在假前提上。

Agent 写入代码和登记进度之间，也可能崩溃或失去连接。下一轮开始时要先检查真实产物，再决定继续还是重做；创建 PR、更新任务这类外部动作同样需要避免重复，靠的是幂等键或者一个能查询的结果标识。

交付给人的内容可以很短：失败原因的证据、代码改动、验证结果、仍然不确定的地方。自动生成了多少文字，不是完成度指标。

## 最容易失控的是「再改一轮」

Jeena 在[自己的翻译实验记录](https://jeena.net/loop-engineering)里描述了一个规划、翻译、批评、修复的循环。执行者与批评者反复来回，却难以收敛到可接受的结果。这是个体实验，不能代表所有循环系统，但暴露的问题很具体：评语持续出现，不代表下一轮有办法解决它。

所以停止条件不能只写一句「做得不够好就重做」。它至少要能回答三件事：这一轮有没有带来新信息、还剩多少预算、这个决定该由谁拍板。落到能写进代码的形态，是几个可以数出来的量：

- 同一错误签名连续两轮出现，且两次改动落在同一处 → 不再重试同样的改法，强制换一个假设。
- 连续三轮没有新增证据——没有新报错、没有新复现、没有新的失败用例 → 停下，把当前产物和已经排除的可能一起交回人工。
- 单个问题的预算用完（轮数、token、墙钟时间任意一项触顶）→ 停下，保留产物和不成功的结论，不要清空重来。
- 验证环节本身起不来（编译不过、环境起不来）→ 单独计一类，不占修复轮数，但仍受总预算约束。
- 需要新的授权（改生产配置、动数据库、发外部消息）→ 立即停下等人，不进入下一轮。
- 两轮评语互相冲突，或者需求本身互相矛盾 → 停下，继续跑也收敛不了。

这些阈值都是示例，具体取多少要看任务的风险和可回滚程度。要紧的是它们必须能被计数——留在提示词里当一句嘱咐，等于没有。

另一个容易被隐藏的成本是 review。假设一天自动产出了十个 PR，团队只能认真看完两个，积压会不断增长。代码与主分支越走越远，后面的集成成本也随之上升。并发上限应该同时看执行费用和人的处理能力，两个上限取小值——先撞到的通常是后者。

这两个上限叠在一起会怎样，算一遍就很清楚。假设循环一天处理十条问题：六条一次修好、两条反复两轮后放弃、两条复现不出来；六条修好的产出六个 PR。一个人一天能认真看完两个，第二天队列里积了四个，第三天八个。积压不会慢慢涨，它会很快顶到一个降不下来的水平——审查速度决定了这条队列只能单向变长。

估算费用时，也不能只用单次成功任务的消耗乘以并发数。失败率、审查轮数、上下文重复加载都会改变结果。先测一批有代表性的任务，记录每一个最终可接受的结果用掉了多少资源，比引用别人晒出的巨额账单更有参考价值——那些数字多半经过转述，任务形态也和你的不一样。

## 人还在哪里

看完停止条件，容易得出「人终于能走开」的印象。人确实走开了，只是换了个位置：从每一轮都在场，挪到了几个固定的检查点上。

必须由人拍板的动作是有限的，可以列出来：合并到主干、发布、改生产配置、动数据库、对外发消息、删除数据。这些动作的共同点是不可逆，或者影响范围超出仓库本身。循环可以把改动准备好，但不能自己按下按钮。

人审查的对象也变了。逐行读代码在自动产出面前不可行，真正能看的是证据链：这次失败的原因是什么、改动落在哪几个文件、验证跑了什么命令、还有哪些地方不确定。前四项齐全的 PR 可以快速过，缺一项的就退回去补。看一个具体修复需要的上下文，比判断整个循环可不可信要少得多——这也是为什么后者更值得占用人的时间。

还有几个只有人能做的决定：第一次上线开不开、范围要不要扩大、停止条件的阈值调不调、某个反复失败的问题值不值得继续投入。这些决定循环给不出，因为它没有「这件事重要吗」的判断依据。

笔者倾向于把人的位置固定成两类：一类是审批，动作不可逆就停；一类是复盘，跑够一段时间回来看积压、看误报、看有没有把简单问题做复杂。中间那些「看着它跑」的时间，才是循环真正省下来的部分。

## 怎么知道这个循环在变好

循环跑起来之后，最容易盯错的指标是「今天开了几个 PR」——它只反映产出，不反映有用程度。更有信息量的是这几个：

- 自动修复被合并的比例。产出很多但大部分被打回，说明分诊或者验证那一步太松。
- 回归率。合进去的修复里，有多少在一周内被回滚或者又改了一次。这一项直接反映验证的质量。
- 复现不了的比例。比例高，通常不是循环的问题，是失败清单本身缺少定位信息。
- 从失败出现到 PR 就绪的时间。它决定了循环有没有真的缩短反馈周期，还是只是把人从写代码挪到了审代码。
- 误报率。循环报出来、人看一眼就知道不用管的问题占多少。误报一多，人就不看 triage inbox 了，循环等于停摆。

这几个数不用做成仪表盘，先人工记一段时间就够。它们的共同点是都能从已有产物里数出来，不需要额外埋点。

## 旧工程经验仍然用得上

调度、重试、状态持久化、幂等和可观测性，都不是随着 LLM 才出现的。把术语逐条对回分布式系统，几乎每一样都有前身：调度就是 cron，外部状态就是一份 KV 或一张表，子 Agent 隔离起来跑就像消息队列里的 worker，验证加反馈重试像带重试的发布订阅，triage inbox 就是死信队列。给它们换一个名字，不会自动减少实现难度。

具体到能直接搬过来用的，至少这几条：

- 幂等靠查询，不靠记忆。重试之前先问「这个操作的结果存在吗」，而不是问「我做过吗」。判断 PR 是否已经创建，要查分支上有没有对应的 PR，不是查本地有没有记过一笔。
- 重试要退避，还要抖动。外部依赖抖动的时候，固定间隔重试会把压力原样叠上去；加了随机抖动，重试才会散开。
- 处理不了的进死信，不要无限重试。triage inbox 就是 Agent 版本的死信队列，进来的每一条都带着失败现场，等人处理。
- 资源要隔离，也要限流。临时数据库、端口、检出目录属于同一类问题——并行度上去以后，冲突的就不只是文件了。
- 每次运行留一条可检索的记录，带上能把同一件事串起来的标识。出问题时先看记录，再猜原因。
- 先在一类任务上跑通。挑仓库里范围最小、结果最容易验证的那一类开工，别一上来就铺满整个组织。

LLM 带来的变化在于输出更难预先穷举，执行路径也会随输入改变。传统 worker 的重试，常常是在同一个操作上重新执行；Agent 的下一轮可能换了工具、改了计划，甚至重新解释目标。因此要记录的除了操作结果，还有本轮到底试图完成什么。前面那条「同一错误签名连续两轮」的停止条件，本质上就是把传统系统里的重试计数，换成了对「这一轮有没有新信息」的判断。

也不能因为机制都是旧的，就认为这次迁移只是改名。有几处确实不一样：

- 判定标准从布尔值变成了分布。传统 worker 的成败由返回值决定；Agent 的产出要靠评分或抽样检查，同一个输入跑两次结果不同是常态。
- 「完成」这个词有三个含义。「模型说完成了」「检查通过了」「需求被满足了」经常不一致，落到状态里要分开记。
- 上下文是有成本的资源。传统系统也省内存和带宽，但不会因为多读了一个文件就影响判断质量——这里会。
- 失败代价不对称。一次自动改错并合进主干，比十次没修好严重得多；这决定了默认动作是「不确定就停下」，「先试一把再说」在这里比其他场景贵得多。

「Loop 比 Harness 更高一级」可以帮助说明视角，但这些词之间没有严格统一的层级关系。定时任务里可以只做一个固定 workflow，Agent 也可以在交互会话里反复检查。用什么标签并不决定系统是否可靠。

笔者打算从一类重复、可验证、失败后容易恢复的工作开始。先观察循环有没有减少人工工作，同时没有扩大错误和积压；等停止条件、恢复和审查都跑顺，再扩大范围。至于人能离开多久，应当由这些结果来回答——现在还没有答案，这个坑先留在这里。
