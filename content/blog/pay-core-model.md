用户在收银台点了两次。第一次没反应，他以为没点上；第二次页面转了几秒，超时了；他退回收银台，换了一张卡重新付。三个动作，在用户那里是「付一次款」，在系统里是三次执行尝试——如果模型把它们当成一回事，出事的时候就要靠猜。

笔者在资金安全方向做过一段时间，见过的重复付款、漏记、账实不符，追下去大多能追到同一个地方：下单、扣款、渠道调用被压成了一条记录。所以这个系列的第一篇不写代码，先写单据——把业务意图和执行尝试分开。这一步怎么拆，后面几篇就能怎么接——账务、网关、退款、对账，都会从这个拆法接着往下写。

## 交易单、支付单、通道请求分别记什么

一笔付款在数据层至少落成三层：

- **交易单**：业务意图。谁买了什么、关联哪个业务订单号、这笔生意值多少钱、最后成不成立。
- **支付单**：一次执行尝试。用什么付款方式、这次要扣多少、发给哪一家渠道、这次尝试本身是什么结果。
- **通道请求**：真正发出去的那一次外部调用。渠道那边的请求号、发出时间、第几次向它发起、原始返回码和报文。

三层之间是 1 比 N 比 N：一张交易单可以挂多张支付单（换付款方式、拆成多笔付），一张支付单可以对应多次通道请求（超时重发、换一家通道重试）。数到最后，一次「付款」可能产生了六条记录，这是正常形态，不是数据脏了。

![一次付款在单据层怎么展开：交易单记录业务意图，支付单记录一次执行尝试并由业务请求号保证幂等，通道请求记录每次外部调用](/images/blog/diagrams/pay-core-model-01-documents.svg)

三层要记的东西可以列得很具体。下面这张表是渠道无关的最小集，具体字段名随各家实现变：

| 这一层 | 必须能回答的问题 | 关键字段 |
| --- | --- | --- |
| 交易单 | 这笔生意是什么、成不成立 | 业务订单号、买卖双方、订单金额与币种、业务状态、创建与过期时间 |
| 支付单 | 这一次打算怎么付、结果如何 | 业务请求号、支付方式、支付金额、目标渠道、支付单状态、关联交易单号 |
| 通道请求 | 这一次到底发出去了什么、对方怎么回的 | 渠道请求号、我方请求序号、请求时间、原始返回码、响应报文或摘要、超时标记 |

三层各有各的生命周期，别指望一个字段说完。交易单跟着业务走，可能挂在那里等很久，也可能被业务主动取消；支付单跟着一次收银台拉起走，用户关掉页面它就该结束；通道请求是分钟级的东西，发起、超时、拿到结果，很快就盖棺定论。混在一张表里，更新最频繁的通道请求会不停去动最应该稳定的交易单，改一个字段要连带想清楚另外两层的语义。

字段的粒度也值得较真。支付单上的金额，记的是「这次尝试要扣多少」，不是「用户应该付多少」——后者属于交易单。组合支付里这两个数字经常不一样，拆单、改价、优惠都在中间动手。把它们混成一个字段，退款时按哪个数退、按哪个数占用额度，会立刻变成要开会讨论的问题。

三层都要留住稳定关联、金额与主体、渠道请求号和结果证据。状态字段只回答「现在是什么」，出了争议要靠这些记录回答「当时到底发生了什么」：用户说他只付了一次，就按业务请求号把支付单和通道请求捞出来，一笔一笔对时间和金额，而不是盯着一个 `SUCCESS` 猜。

组合支付会让数量关系再长一层。一笔订单用了部分余额加部分银行卡，各自是一条独立的资金来源记录，金额和状态必须分开记——余额那一半成功了、银行卡那一半失败了，跟整笔失败是两件不同的事，处理方式也不同。

## 渠道说「成功」了，就一定成功了吗

这一层的取值至少要分成四类——明确成功、明确失败、处理中、未知。把后两类压进失败，是重复扣款最常见的起点。

渠道返回 HTTP 200，多数时候只表示「请求被受理」，不代表这笔钱已经到账；反过来，请求超时也不代表扣款没发生，渠道可能已经处理完，只是响应没回来。受理和最终结果是两件事，中间隔着一整段渠道内部的流程：验签、风控、扣款、记账、回通知。HTTP 那一层的成功只覆盖到这段流程的入口。

这五个取值各自对应不同的下一步：

| 状态 | 含义 | 本地该做什么 |
| --- | --- | --- |
| 受理 | 渠道收下了请求，结果还没有 | 等待通知或安排查询 |
| 处理中 | 渠道明确答复还在处理 | 退避后继续查询 |
| 成功 | 有明确凭据证明扣款完成 | 推进支付单和交易单 |
| 失败 | 有明确凭据证明未扣款 | 可以结束这次尝试 |
| 未知 | 没拿到结果，也不确定渠道收到了没有 | 留着追踪，禁止当失败处理 |

「处理中」和「未知」的差别不是抠字眼：前者是渠道告诉你在处理，等到结果就行；后者是本地根本不知道渠道收到没有，得主动去问。把未知当作失败，代价很直接——用户看到支付失败会再付一次，第二笔扣款就出现了，而第一笔很可能已经成功。更麻烦的是后面那步：为了「修复」失败，系统可能重新发起一次扣款，这一次没有幂等键保护，因为对本地来说它就是一笔新业务。

映射渠道返回码的时候也别急着归一。请求参数错误和「已扣款但通知失败」不能都收成一个 `FAILED`：前者可以直接结束这次尝试，后者反倒要按成功推进。归一之后的本地状态是为了让上层好处理，原始渠道代码和报文得原样留着，映射规则写错了才有机会回头重算。渠道那边一个笼统的「处理失败」，到了本地可能对应完全不同的两种现实，这是通道适配层最需要小心的地方。

补齐最终结果有三个入口：主动查询、异步通知、对账。它们会重复、会乱序，甚至成功通知比对账结果先到。所以本地更新得守同一套状态迁移规则，而且状态要能单调推进——已经确认成功的支付单，后面再来一条失败通知，不能把它退回去，否则会产生一笔已经发生的钱在我们的账上「没有发生过」。

一条支付成功通知进来，按本地已经攒下的信息分流，比按通知本身分流更靠得住：

| 本地现状 | 该做什么 |
| --- | --- |
| 交易单已由当前这张支付单完成 | 重复通知，回同一个处理结果，不再改动 |
| 交易单已由另一张支付单完成 | 重复支付，登记异常并按规则处理多付部分 |
| 交易单已关闭、钱确实扣了 | 不能履约就创建可追踪的退款任务 |
| 交易单还挂着，但支付单已过有效期 | 按状态机判定，该成功就成功，该关就关 |

四行里没有一行是「收到成功就推进订单」。分流依据是本地状态，通知的内容只是输入之一——它只说明渠道那边发生了什么，能不能接受，得看本地处在哪一步。

主动查询要带对参数，不然问了等于没问。能唯一确定渠道侧那笔付款的，通常是渠道请求号；只有业务请求号时，多数通道会要求同时给出请求时间和金额。查询本身也会失败、也会超时，那种情况返回的是「还没问到」，不能当成一笔新的结论写进状态。

对账的粒度比查询粗，但覆盖更全。它要按渠道账单的时间口径取数，以渠道侧记录为基准，把本地认为成功、渠道账单里找不到的记录挑出来——这类单边账正是「本地成功、钱没动」的典型形态，而对账这条线准备单独写一篇展开。

## 重复付款是怎么发生的

把重复付款归成四种形态，处理方式就分得开了：

| 形态 | 触发路径 | 结果 |
| --- | --- | --- |
| 同一次尝试被重复发送 | 超时重发、框架自动重试 | 同一张支付单下的两条通道请求，两边都成功就是重复付款 |
| 同一笔付款意图被重复执行 | 用户刷新、客户端重试、消息重复消费、上游重放 | 两条支付单同时存在，各自都合法 |
| 换了执行路径又没关掉旧的 | 用户换付款方式、网关超时换通道 | 旧路径结果未知的情况下新路径成功，两笔都扣了款 |
| 结果回来以后被重复入账 | 回调、主动查询、对账三个入口的结果叠加 | 钱扣了一次，账上记了两次 |

前两种的区别值得记牢：第一种是「重试」，第二种是「另起一单」。从用户的视角看都是「付了两次」，处理方式却完全相反——重试要复用同一张支付单，另起一单要确保旧的那张已经关闭。分不清这两件事的系统，要么把正常换付款方式的用户挡在门外，要么给重复扣款发一张通行证。

真正难防的是第三种，因为它跨了两个团队的责任边界：网关只关心「这一笔要送到哪家通道」，支付核心只关心「这张支付单现在什么状态」。路由决定换通道的那一刻，如果没人去关原通道的未知结果，两笔扣款就都成立了，而且事后追查时两边都有完整日志，看上去谁都没做错。

## 状态未知时到底该做什么

未知不是「等一会儿再说」，它有一串具体的动作，而且顺序不能反：

先原样保留状态，不要加超时失败、不要让它被关单、也不要顺手释放它占用的额度。未知态下释放额度是个很隐蔽的坑——额度一旦放出去，同一笔预算可以再被占用一次，等未知那笔最终成功，就超占了。

接着安排追踪。要追的东西至少包括：渠道请求号、请求时间、原始返回码或错误信息、这笔支付单对应的交易单，以及已经追过几次、追到什么时候为止。没有追踪期限的未知态等于挂了，没人会回来处理它。

然后按通道能力选路径。支持单笔查询的通道，按渠道请求号去问最终结果，问不到就退避重试；不支持查询的通道，只能等异步通知或等对账，那就把这条记录挂进待对账的清单，别指望通知一定会来。

查询返回失败本身不算结论。「查询接口超时」「查不到这笔单」都不构成「未扣款」的证据，它们只是说明这一次没问到。把它当成失败推进，等于用一次网络抖动给一笔可能成功的付款盖章。这个区分不是支付独有的：几年前在[《CAP 的边界：分区期间给不出的承诺》](/blog/ha-about-cap)里，同一件事是从分区那一侧写的——超时和报错是两种不同的结果，前者只说明结果未知。

最后是对账兜底，以及一个容易被忽略的收尾：处理完的未知记录要有出口。查明确实成功、确实失败，或者转成异常单等人处理，三条路都行，唯一不行的是让它一直挂在未知里——等到用户来投诉才发现，是最贵的一种发现方式。

## 幂等键要在发起付款之前定下来

上面这些重复通知之所以还能处理，靠的是有一个不会变的业务请求号。它得在发起付款之前就定好，作用域、有效期和参与签名的参数一起定死。事后补是补不回来的：请求已经带着旧参数发出去了，你改不了。

作用域也不是随手一填的事。同一个业务请求号，在支付域里指的是「这个业务系统、这个场景、这一次收银台拉起」，到了通道路径上还要带上渠道和支付方式，否则用户从银行卡换成余额时，两次意图会撞在同一个 key 上，后一次被当成重复请求丢掉。范围划大了会误伤正常的新付款，划小了挡不住重复提交，这个取舍得按业务能给到什么粒度的请求号来定。

规则可以压成两句：同一个业务请求号只能落到一张支付单；重试是同一张支付单再加一次通道请求。代码里最容易踩的坑，是把幂等键交给通用 HTTP 重试去生成——每次重试新生成一个请求号，等于把幂等丢了，通道眼里那就是两笔新付款。

落到报文上，重试请求带的东西长这样：

```json
{
  "idempotency_key": "trade-20231121-8842",
  "amount": 1990,
  "currency": "CNY",
  "payment_method": "balance",
  "trade_no": "T20231121001"
}
```

`idempotency_key` 由业务侧生成，从用户点下确认那一刻就固定，页面刷新、客户端重试、网关重发都带同一个，落在支付单上就是那个业务请求号。金额、币种、付款方式这些参与签名的参数跟着一起走，通道才有依据判断「这是同一个请求」还是「参数变了的新请求」。

反过来，用户真的换了付款方式，就该新开一张支付单。旧单能不能关掉、它占用的额度还在不在，决定了这次换法是不是干净。该新开的时候不开，用户会被锁在一张永远付不成的单上，反复提交也还是那一条未知的记录；不该新开的时候新开了，两次扣款就各自有了合法外衣，事后连「这算不算重复支付」都要先吵一架。

这套做法不是某一家独有的。[Stripe 的幂等请求](https://docs.stripe.com/api/idempotent_requests)里，相同 key 会返回首次请求的结果，但 key 有保存期限，跨账户和并发场景也有各自的边界。接入别的通道时按各自文档来，别假设一套 key 规则永久有效——期限过短，隔天重试就变成了新付款；跨主体不隔离，A 商户的请求号会挡掉 B 商户的。

## 关单和支付成功撞在一起

本地订单到期，并不能撤销渠道里已经完成的那笔付款。关单任务和成功通知并发的时候，两边都只看到自己那一半事实，于是本地订单关了、用户的钱也扣了。

处理这类碰撞要在本地事务里做两件事：检查当前状态、原子地更新，再把后续要做的动作落成任务。具体的分流看本地已经攒下了什么——支付单已经成功、交易单却被另一笔付款完成，就登记重复支付异常；交易确实没法履约，就创建可追踪的退款任务等最终结果；而如果这一笔的状态还是未知，就不能直接关单放行，得留着继续追。

「状态未知就不能关单」这句听起来像在拖，其实是在承认一个事实：本地订单和渠道侧付款是两套记账，它们的结论不一致时，真正的麻烦在于钱少了或者多了，而不是订单关得早。查清楚之前把订单关掉，等于把一次可能的重复扣款从「待追」变成「没人知道要追」。

分布式锁可以帮忙协调同一时刻的并发，但真正的保证来自数据库约束和带状态条件的原子更新，锁本身不产生约束。还有一点别弄反：渠道操作从头到尾都不能被包进本地事务，数据库回滚不了已经扣掉的款。

## 支付成功不等于已经结算

支付、清算、结算这三个词在不同业务和机构层次上用法不太一样，工程上至少要分清它们各自的完成条件：付款请求是不是成功、各参与方的应收应付怎么算、钱有没有按约定完成划拨。

支付回调成功不能解释成钱已经进了商户账户。清算算的是应收应付，出的是对账单；结算才是真的划钱。中间还夹着结算周期、手续费扣除和结算安排，这些以合同和渠道资料为准。对账为什么非要拿渠道账单和本地流水两边对，原因也在这里——本地成功只证明我们这一侧的记录，渠道账单才知道钱到哪一步了。

同一笔付款，三个概念落地的时刻可以隔好几天，而系统的对外表现只有一个「已支付」的订单。这中间的落差靠流程补，不靠把三件事塞进一个状态字段。

## 那到底怎么算追踪清楚了

回到开头那个点了两次的用户。建模时最值得推演的是不顺利的那几条路径：请求发出去以后响应丢了、回调重复到达、关单和付款成功撞车、组合支付里一部分资金来源失败。每一种都能在某一层找到对应记录，并且知道下一步该做什么——这才叫追踪清楚。

至于账务那一层，它看起来最没有技术含量，改起来的代价却最高。账务打算接着写一篇：钱记在哪本账上，以及余额为什么会变成瓶颈。
