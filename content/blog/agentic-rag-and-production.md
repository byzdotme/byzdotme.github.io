[上一篇](/blog/rag-full-stack-guide)把链路走了一遍：文档准备、召回、重排、评估，讲到切分时留了一句——小块检索、父块返回的具体做法和代价准备另写一篇。这篇就从那句话接着往下写。

不过父块只是错误的一种形态。链路真跑起来之后，问题不会按章节排队。笔者见过的几种长相是这样的：命中了“该接口支持重试”，却漏掉了同一段里的“必须沿用首次请求的幂等键”，答案于是鼓励人放心重试；问“退款失败后钱多久回到用户账上”，答案需要退款接口、账务入账和渠道对账三份文档凑在一起，而检索只挑回了最像的那一份；再有一种是文档都齐，v1 和 v2 的规则都在库里，模型把两版的说法缝成了一段看起来很完整的解释。

这三种错，修的地方并不相同。Parent-Child 改的是返回的上下文，Contextual Retrieval（上下文检索）改的是索引里的内容，Self-RAG 和 CRAG 在检索与生成之间加判断，GraphRAG 多建一层图与摘要，Agentic RAG 则把“下一步查什么”交给模型决定。它们可以组合，没有必经的先后顺序，也不存在“上了 Agentic RAG 就都解决了”这回事。这几条路线深浅不一，笔者自己也是边看边试，下面尽量写清楚每条路多花了什么、换回了什么。

这篇按“错长什么样、该改哪一环”的顺序走一遍，最后把这些改法的代价摆在一起比。

## 命中了半句话，先把上下文补回来

接口文档里写着：“该接口支持重试，但必须沿用首次请求的幂等键。”检索只返回了前半句，生成模型就很容易把后半句省略掉——它没有撒谎，它只是没看到。此时继续搜相似的句子，未必比直接取回这句话所在的小节更有效。

Parent-Child 的做法是保留两种粒度：小块进入索引，命中后根据 `parent_id` 取回较大的段落或小节。

![用子块匹配查询，再按 parent_id 取回包含约束条件的父小节](/images/blog/diagrams/agentic-rag-and-production-01-parent-child.svg)

父块回补之后，有几件事必须跟着处理。重复的父块要去掉：十个子块可能来自同一小节，把整节复制十次只会挤掉别的候选；父块还要限制总长度，命中一个句子不等于要把整章塞进去。权限和版本也得重新检查一遍，小块允许访问不代表父块里的其他内容也允许，索引里存的是旧版父块时更要把版本对回来。

去重还有反向的坑。候选里十个子块合成一个父块之后，送去生成的可能只剩一两条内容，覆盖面反而比原来窄：本来能靠多个片段互相印证的结论，现在只有一个出处。所以去重之后通常要看一眼最终上下文里还剩几个不同的来源，数量和问题复杂度大致匹配才算正常。

代价主要落在返回侧。索引里要多存一层父子映射，检索时多一次按 `parent_id` 的查询，返回的 token 数随父块大小上涨。父块选得太大，无关内容会把约束条件一起稀释，这和上一篇里“塞进上下文的块不是越多越好”是同一件事。

同一族里还有两个变体。Sentence Window 命中句子后附带前后各若干句，回补边界是句子；Auto-Merging 在多个相邻子块同时命中时合并成父块，回补边界由命中的分布决定。选哪种取决于缺失的条件离命中点多远：约束通常紧挨着规则，句子窗口就够；约束写在小节开头的适用范围里，那就得回到小节。

粒度上有个常见的配法可以参考：子块取 200 到 300 token，父块取 800 到 1500 token，前者保证检索够准，后者保证条件凑得齐。`parent_id` 之外再存一个块在父块里的位置，合并多个子块时才能按原文顺序拼接，而不是按命中分数排——顺序打乱之后，读者看到的因果关系会反过来。

回补和重排的先后也得定下来。先重排再回补，排序看的是子块，精度不受影响，但回补之后上下文会膨胀，token 预算变得难控；先回补再重排，重排能看到完整的语义单元，判断更准，代价是每个候选都变重，重排一次要读更多内容。检索量大、父块又大的场景，通常是先重排、再按最终名额回补，把膨胀控制在最后一步。

判断回补有没有用，看两件事就够了：缺失的条件回来了没有，噪声增加了多少。如果补完父块答案还是漏条件，问题多半不在上下文粒度上——再调父块大小只是换个地方漏。还有一种情况是条件压根不在同一份文档里，比如适用范围写在总则、细则写在接口文档，这时候回补再大的父块也没用，得换下面的思路。

## 连块都找不到，再考虑给索引补语境

还有一种情况更麻烦：要补的那句话根本不在候选里。文档里写着“它的超时时间为 30 秒”，人读整篇知道“它”指哪个服务，单独拎出来的块却没有这个信息。查询“退款服务超时”时，向量检索很难把这一块排上来——它长得不像在讲退款。

Anthropic 的 [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) 在入库前给每个块补一句语境：把块放回原文，让模型用一两句话说明它讲的是什么、属于哪份文档的哪一节，再把这段语境拼在块前面，一起做向量和 BM25 索引。原文报告，组合 Contextual Embeddings 与 Contextual BM25 之后，top-20 检索失败率从 5.7% 降到 2.9%。这里的 49% 是该实验的相对降幅，不能写成所有知识库都会提升 49%。

它和 Parent-Child 改的不是同一段。一个是把信息提前写进索引，检索链路一行不用动；一个是索引不变，在返回时把上下文补回来。这也意味着两条路可以同时用，不必二选一。

补出来的那句语境大概是什么样，可以感受一下：《退款接口说明》v2 ·「超时与重试」一节，本块给出超时后查询处理状态时，能否重试以及幂等键的要求。它不解释规则内容，只交代这一块在讲什么、属于哪里，让检索在缺主语的情况下也能把它排上来。

补语境的成本主要在索引期。每个块都要生成一次语境，块数是百万级时这笔调用开销不小，好在整篇原文可以放进带缓存的提示里复用，单位成本能压下来；代价是重建索引的时间明显变长，语料更新频繁时要想好是增量补还是整批重来。语境通常控制在一两句话，写成段落摘要就本末倒置了——它的作用是让这个块能被找到，不是替代这个块。

落地时一般会建两套索引：一套是带语境的文本，服务于 BM25 和向量检索；一套是原文块，服务于展示和引用。两边用同一个块 ID 关联，检索走前者，回答里的出处回后者。这样也能顺带解决一个尴尬：模型看到的句子和用户点开看到的句子不一致时，没人说得清哪边是对的。

生成的语境本身也可能写错，所以工程上一般把它和原文分开存，展示和引用都回到原文。文档标题、所属产品、章节路径这些确定信息可以直接从元数据补上，只有这些还不够时才交给模型推断。这样出问题也更容易定位：到底是原文写得不清楚，还是索引前的那句解释添了错。

也不是每个块都值得补。收益集中在那些缺主语的短块：代词多、结论句多、表头在上一段的段落。一张完整的参数表、一段自包含的代码，本身已经把“这一块在讲什么”说清楚了，补出来的语境通常只是复述标题，白花一次调用。预算有限时先挑这类块试，比全量重跑一遍便宜得多。

## 文档都在，只是版本拼到了一起

开头说的第三种错跟前两种都不一样。检索没问题，召回的都是相关文档，问题是 v1 和 v2 同时在库里：老版本写着“超时后可以直接重试”，新版本改成了“先查询处理状态再决定”，模型两边各取一半，缝出一段内部自洽、业务上却不存在的规则。

根子在元数据。每份文档要带着版本、生效时间和适用范围入库，检索时按默认口径过滤——多数人只该看到当前生效的那一版。旧版本也不是删掉了事：故障复盘、历史工单、审计追问都要查当时生效的规则，所以常见做法是把“当前生效”和“历史”划成两个检索范围，默认查前者，需要时显式指定版本。

提示词里同样要写清楚：资料跨版本时不许混着用，遇到冲突要么按生效时间取最新，要么把冲突原样交出来。这句话听着像废话，可不写它，模型面对两种说法时往往挑一个看起来更全的，或者干脆把两者缝起来——缝出来的规则，两个版本都不认。

评估集里值得专门留几个跨版本的问题，比如“去年这条规则是什么样”。它们同时考验版本过滤和拒答：答成最新版本算错，答成两版的混合更错。

“去年是什么样”这类问题还额外要求索引支持按时间点查。做法通常是给每个块记一对生效起止时间，检索时先按时间过滤再比相似度；只靠向量检索答不了这种问题，它没有时间的概念，只会把两个版本一起排上来。

## “再检查一次”有不同实现

Self-RAG 和 CRAG 都会判断检索回来的内容有没有用，但它们不是给普通 prompt 加一句“请反思”就能复现的。

[Self-RAG](https://arxiv.org/abs/2310.11511)训练模型在生成过程中输出反思标记：这一步要不要检索（Retrieve）、检索到的段落相不相关（IsRel）、写出来的论断有没有被段落支持（IsSup）、整段回答对用户有没有用（IsUse）。这些标记是模型学会的输出，不是提示词里加一句话就能出现的，所以它牵涉训练和推理策略两部分。界面上多出一个“自检”步骤，并不等于用了同一种方法。

[CRAG](https://arxiv.org/abs/2401.15884)走的是另一条路：检索之后加一个检索评估器，给结果分档，再按档位决定后续动作。判断为可用时，把候选文档拆成细粒度片段再重组成更干净的知识条；判断为不可用时，丢弃这批结果、换一个来源（论文里用的是网页搜索）；判断不了时，两种做法都用一遍再合并。评估器可以是一个小的检索评估模型，不必让同一个大模型既当裁判又当选手。

两条路的开销也不一样。Self-RAG 需要有一个会输出反思标记的模型，落到自建场景通常意味着微调加上推理侧的配套；CRAG 多一次评估调用，换来源那一步还会把外部内容拉进上下文，延迟和可信度都要重新算。

CRAG 里最值得借鉴的其实是那个“分档再动手”的结构。评估器不必很贵，一个小模型给出可用、不可用、说不准三档就够；分档之后每一步做什么是写死的规则，可测、可回滚。真正难的是阈值：卡得太松，差结果照样进生成；卡得太紧，本来能用的资料被丢掉，系统表现成“什么都不知道”。阈值要拿错题集来定，而不是拍一个分数。

评估器的冷启动也有个务实路径：先拿人工标过的错题当样本，标注不够时用大模型顶一阵，等样本攒到几百条再换成小模型。换的时候要拿同一批样本对比两边的判断，否则阈值会跟着模型一起漂，之前调好的分档标准悄悄失效。

Self-RAG 的反思标记也有个容易被忽略的好处：`IsSup` 这类判断把“这句话有没有依据”从人肉检查变成了模型输出的一环，批量筛样本时很有用。代价是这套能力长在模型里，模型一换就得重来一遍。

放到一次具体提问上看，这些标记起的作用很直白。问“退款接口 v2 的重试条件”，Retrieve 决定要不要去查库；查回来三段内容，IsRel 把只讲到 v1 的那段标成不相关；写答案时每写一句，IsSup 检查它有没有段落撑着；最后 IsUse 判断整段回答是不是在回答用户问的那件事。四个标记里任何一个不准，最终答案都会跟着偏，这也是它必须靠训练而不是靠提示词的原因。

对公司的内部规则来说，公开网页通常替代不了内部知识库。查不到退款政策时，可以请求补充文档、明确缺少依据，或者只回答能确认的那部分。退回模型内部知识作答，必须是产品明确允许的行为：“无知识库支撑”几个字并不能让猜出来的业务规则变得可用。

## GraphRAG 解决的是另一类查询

问“某个接口的重试条件是什么”，相关小节通常就够了。问“过去一年的事故主要集中在哪些依赖关系上”，答案可能散在整个语料库里，需要归纳实体、关系和主题，这种问题不是把 top-K 调大就能解决的。

微软的 [GraphRAG](https://microsoft.github.io/graphrag/)会从文本里抽取实体和关系，在图上做社区划分，再为每个社区生成摘要，用它们支撑两类查询：局部查询沿着实体附近的关系和原文片段找答案，全局查询则在社区摘要上做一轮 map-reduce，把散落的主题归拢成结论。这两类查询问的东西不一样，索引也是为它们分别准备的。

社区划分是分层的，从大到小好几级，这一层设计直接决定能回答多粗的问题。层级太少，摘要太笼统，回答不了“主要集中在哪几类依赖”；层级太多，每一级都要生成摘要，索引成本跟着翻。全局查询还要把问题发给大量社区摘要再汇总，一次提问的 token 开销可能比普通检索高两个量级。

成本集中在索引期，而且不便宜：实体关系抽取要为每个块调用模型，社区摘要还要在抽取结果上再跑一轮。文档更新之后，受影响的社区和摘要要重新生成，更新频率高的语料会把这项开销放大。抽取本身的错误也会一路传下去：两个同名服务被合并成一个实体，后面所有基于关系的分析都建立在错误的前提上。

关系密集、实体名称稳定的语料才值得建图，比如服务依赖、组织架构、事故与变更之间的关联。文档以流程说明和字段解释为主、问题也多是“某个字段是什么意思”，建图带来的那层结构基本用不上。

两类查询的产出也不一样。局部查询的答案是几段带出处的原文，和普通 RAG 看起来差不多；全局查询的答案更像一份小结，比如“事故集中在上游依赖缺少超时、以及配置变更没有灰度这两类关系上”，底下再挂几个代表性社区和它们的原文出处。前者要求引用准确，后者要求归纳站得住，评估方式也得分开设计。

所以笔者会先收集那批“用局部片段怎么都答不好”的问题，确认它们确实需要跨文档归纳，再评估建图这件事。某个字段总查不准，还不足以说明系统需要 GraphRAG。

## 什么时候让 Agent 决定下一次检索

对“比较两个版本接口的退款限制”这类问题，预先安排两个查询就够了，没必要把控制权交出去。只有后一步依赖前一步发现的信息时，自适应查询才更有意义：先查这次故障涉及哪些服务，再拿服务名去找各自的变更记录——第二步的查询词，第一步之前根本写不出来。

Agent 手里的工具通常不止一个：内部文档检索、网页搜索、结构化数据库查询、计算器。模型要挑的不只是查询词，还有去哪查。工具描述得写清楚它返回什么、什么时候该用、什么时候不该用；描述含糊的时候，模型会把网页搜索当成万能兜底，而网页上的说法和内部规则冲突时，它未必知道该信哪个。

多轮之间还要记住已经查过什么、拿到了哪些证据、哪些方向已经排除。这些状态值得显式存下来，而不是靠模型自己回忆对话历史——上下文一长，它对自己查过什么这件事的记忆，比对人家的文档还不靠谱。

多跳的样子也不复杂。问“退款失败后钱多久回到用户账上”，第一跳查退款单的状态流转，知道失败要分“已受理未处理”和“已拒绝”两种情况；第二跳才拿这两个状态分别去查账务入账时间。第一跳之前，第二步该查什么根本写不出来，这就是它和“预先安排两个查询”的分界线：能不能在提问的那一刻把子问题列全。列得全就别交给模型，列不全才值得上循环。

检索工具应该返回可追溯的片段，而不是拼一大段纯文本。一个与具体框架无关的返回结构可以是：

```json
{
  "query": "退款接口 v2 重试条件",
  "hits": [
    {
      "document_id": "refund-api-v2",
      "section": "超时与重试",
      "revision": "example-revision",
      "source_url": "https://docs.example.com/refund-v2",
      "text": "示例内容：超时后先查询处理状态……"
    }
  ]
}
```

上面只是结构示意，文档地址和内容均为占位示例。身份、租户、权限过滤条件由服务端根据当前用户注入，不交给模型任意填写。`revision` 这一项也建议一并返回：模型在写答案时能看到资料属于哪一版，遇到跨版本的说法才有机会主动说明，而不是默默合并。

![Agent 检索后检查证据，充分则回答，不足则在预算内补查，超限或无新增证据时停止](/images/blog/diagrams/agentic-rag-and-production-02-retrieval-loop.svg)

循环要能停下来，得先定义清楚什么叫停。至少要有四种出口：证据已经足够回答问题；预算用完，包括轮数、总耗时和 token 上限；连续两轮没有拿到新证据；以及资料里确实没有这条内容，那就明确说明缺少依据。第三种最容易被忽略——模型换了几个近义词再查一遍，看着像在推进，实际上检索结果一个字没变。

“证据足够”这一条最难写具体，它没有客观标准，全交给模型自己说又会一路说够。工程上一般把判据摊开：问题里的每个实体都要有对应段落，答案至少要能引用两段相互独立的来源，关键条件不能只出现在一个块里。判据越具体，循环越不容易在本该停的时候继续转。

评估这类系统不能只看最终答案。要拿一条固定的查询流程做对照，看新增的检索有没有带来新证据、正确率有没有提高，以及多花了多少时间和 token。一次复杂问题上的成功，证明不了每个问题都值得走多轮。

## 拿一个错误走一遍

前面这些改法听着都不复杂，难的是不知道该动哪一个。拿开头那个错误走一遍：问“退款接口超时后能不能重试”，答案说可以重试，没提幂等键。

第一步先别动手，把错误定位到链路的某一段上。把那次检索的中间结果翻出来——原问题、召回的块、重排后的顺序、最终传给模型的上下文，这些是上一篇里特意要求留下的：

- 候选里压根没有写着幂等键的块：先看它在不在库里，再看是不是被切走了。规则和条件在切分时分家，要回去改切分；块里写着“它的超时时间为 30 秒”这种缺主语的句子，那是 Contextual Retrieval 的活。
- 候选里有，重排后没进上下文：要么是截断名额太少，要么是排序把带条件的块压到了后面。这里动的是重排和截断，跟索引没有关系。
- 上下文里有那句约束，答案还是没提：问题在生成侧，检查提示词有没有要求逐条对齐资料，以及模型是不是把两段不同来源的内容缝到了一起。

第二步才是动手，而且一次只改一处。改完拿同一批错题重跑，先看这一类错误减少了多少，再看别的类有没有被带坏——父块调大之后，原本及格的“要点齐全”那一类很可能因为噪声变多而掉下去。

第三步是决定留不留。一个错误现象往往能指向好几种改法，最后留下的应该是那种在这批错题上确实减少了对应错误、又没把成本推高一个量级的做法。

走完这三步还有一件事要做：把这次的错题补进评估集，写清楚它属于哪一类、正确答案该包含哪些条件。同一类错误再出现时，评估集能立刻告诉你它是新问题还是老毛病复发——没有这一步，下次只能靠记忆判断改动有没有用。

## 这些改法各自的代价

把六条路线摆在一起，能看出它们改的位置、一次性投入和每次请求的开销都不是一个量级：

| 路线 | 改的是哪一段 | 一次性成本 | 每次请求的额外开销 | 主要风险 |
| --- | --- | --- | --- | --- |
| Parent-Child | 返回的上下文 | 多切一层块，存父子映射 | 返回 token 变多 | 父块过大挤掉别的候选 |
| Contextual Retrieval | 索引里的块内容 | 每块生成一次语境，重建索引 | 基本不变 | 语境写错，索引重建慢 |
| Self-RAG | 检索与生成之间的判断 | 需要会输出反思标记的模型 | 多几次生成 | 复现门槛高，得先有训练能力 |
| CRAG | 检索结果的评估与补救 | 加一个评估器 | 一次评估调用，可能加搜索 | 评估器误判，外部内容不可信 |
| GraphRAG | 索引期的图与摘要 | 抽取、社区划分、摘要生成 | 查询走图或走摘要 | 抽取错误传播，更新要重跑 |
| Agentic RAG | 检索的流程控制 | 工具定义与状态管理 | 多轮检索，上不封顶 | 循环不收敛，成本失控 |

便宜的改动集中在两头：给索引补语境、回补父块，都是确定性的工程活，做完就能看到效果，也不引入新的失败模式。贵的那几条要么需要训练能力，要么把成本推到每次请求上——多轮检索的账单是按问题复杂度浮动的，复杂问题上的收益很容易被平均成本抵消。

几条路线叠在一起时，效果也不是简单相加。Contextual Retrieval 让块自己带上了主语，父块回补的收益就会小一截；反过来，父块变大之后，重排能起到的作用也在下降，候选本来就没剩几条，排序差异有限。改动越多，越难说清是哪一处起了作用，所以一次只上一处，既是省钱，也是保住判断力。

顺序由失败样本决定，不由名词的新旧决定。同一批错题跑一遍，哪条改动减少了对应的错误就留下，没减少的就不必因为名字更先进而留着。还有一条更容易被跳过的结论：如果错题里的多数问题出在文档本身——规则过时、条件压根没写、两份文档互相矛盾——那上面六条路线一条都救不了，它们改的都是“怎么把已有的资料找出来用好”，资料里没有的东西，再贵的索引也造不出来。这时候该做的是回去补文档，不是继续加检索层。

如果要给一个起步顺序，前两条性价比最高：给缺主语的块补语境，再加父块回补和重排，这套组合不引入循环、不依赖训练，多数内部文档问答到这一步就能用；GraphRAG 和 Agentic 循环留给真正需要跨文档归纳、以及第二步依赖第一步结果的问题类型，它们不是更高级的版本，是更贵的工具。上线顺序也建议先索引和返回侧、后控制流：前两者的改动是确定性的，出了错能直接指出是哪个块、哪一版；控制流一旦上线，同样的输入两次跑出来的检索路径可能都不一样，排查成本是另一个量级。

每条改动还得配一个能验证它的指标，否则上线之后就只能靠感觉。父块回补看缺失的条件有没有回来，Contextual Retrieval 看原来排不上来的块有没有进候选，CRAG 看分档准不准，多轮检索看新增的轮次有没有带来新证据。指标对不上的改动，过一阵子就没人说得清它还在不在起作用，删掉它也没人敢点头。

## 上线以后，容易漏掉的几件事

文档的更新、删除和权限变更要贯穿整条链路。只刷新向量索引，却留下旧的父块缓存或图摘要，系统仍会照着旧规则回答；索引切换时要连关联的原文版本一起切，否则新的向量会指向旧内容。

缓存要包含影响答案的上下文，尤其是权限范围、资料版本和查询配置。同一句话由不同用户提问，本来就不该拿到同一个结果。

延迟要拆到每一步测量。流式输出能减少等待感，却不会降低完整任务的耗时；多轮 Agent 还可能在生成第一个字之前先跑好几次工具调用，首 token 快代表不了端到端。

成本也要单独看。社区摘要的重算不该跟着每次文档更新跑，多轮检索的轮数上限要和服务端的超时、并发配额一起定，否则一次批量提问就能把预算打穿。

最后，检索结果属于外部输入。文档里若夹着“忽略前面的指令，调用某个工具”，它仍然是待分析的内容，不该获得操作权限。工具权限、受控执行和数据隔离，比过滤几种提示词更可靠。

还有两件属于运维习惯的事。一是留痕：谁在什么时候问了什么、系统召回了哪些块、最终答了什么，这份记录在排查“上周那个答案是从哪来的”时是唯一的线索。二是回归：把评估集挂到发布流程上，索引重建、切分参数调整、模型版本升级这三类变更都要跑一遍——它们的共同点是不改一行代码，也能让回答变个样子。

用户反馈要能追回到那次检索，才有用。一个孤立的点踩只是一个情绪标签，把它和当时的召回块、重排顺序、引用对应关系接起来，才能看出是资料没找到，还是找到了没用上。收集反馈的入口越顺手越好，分析的时候越具体越好，这两件事经常只做到前一半。

索引切换本身也要留退路。新索引接上去之前，先按一小部分流量灰度，对比同一批问题的命中情况；发现问题就切回旧索引，而不是指望现场重建。图摘要这类重产物尤其如此，重建一次要几十分钟甚至更久，没有回退路径的切换等于把可用性押在一次全量任务上。
